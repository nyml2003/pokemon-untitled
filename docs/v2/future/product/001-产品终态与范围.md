# 产品终态与范围

> 分类：未来；起草：2026-07-21。
> 状态：产品提案。本文描述目标体验与边界，不描述当前已经具备的完整产品。

## 结论

终态应是一款“规则可验证、内容可持续创作、AI 可受限接入”的单人宝可梦式 RPG。玩家面对的是完整的世界探索、队伍成长、回合制战斗、NPC 互动、训练师挑战和存档延续。AI 不是游戏状态的主人。它只在对战决策、内容创作和少量受控角色表达上提供能力。

项目最重要的选择是把可复现性置于生成性之前。游戏必须能够在没有模型、没有网络、没有新内容生成任务时保持可玩。模型带来的价值应是更丰富的对手、更快的编辑器创作和更高质量的内容迭代，而不是让基本循环依赖外部服务。

## 目标玩家体验

玩家从一个小型起始区域开始。初始区域不需要有完整地区规模，但必须已经展示最终系统之间的关系：地图连接、可见 NPC、可交互事件、草丛遭遇、训练师战、恢复或商店、任务 flag、队伍状态和存档。

玩家的正常循环如下：

```text
观察地图
  -> 移动、转向、交互
  -> 触发脚本、奖励、warp、遭遇或训练师视线
  -> 进入回合制战斗
  -> 选择招式、换人、道具或逃跑
  -> 对方由规则型策略或 AI 在相同可见信息下行动
  -> 战斗结果生成受限状态补丁
  -> 世界、队伍、金钱、flag 和 NPC 状态更新
  -> 玩家继续探索、保存或返回标题
```

这个循环必须有明确的“当下状态”和“长期状态”。当下状态包括当前场景、菜单焦点、对战动画回放、对白页数、等待的输入和模型请求状态。长期状态包括玩家位置、队伍 HP/PP/经验、背包、金钱、任务 flag、已击败训练师、已领取物品、世界对象状态和存档版本。两者不能用同一个无边界结构承载。

## 产品承诺

### 1. 离线优先

玩家可以断网游玩核心剧情和全部基础对战。若选择启用云端模型，对战 AI 可以退化为本地启发式策略；创作工具可以保留未生成的任务并允许手工编辑。任何请求失败都不应让存档无法加载，或让正在进行的战斗失去可恢复状态。

离线优先不是“永远不联网”。它是状态所有权的声明：联网只能提供建议、候选或策略，不是游戏事实的唯一来源。联网能力的请求、缓存、失败、重试和费用都在 adapter/runtime 层；核心只接收已经冻结的输入和输出。

### 2. 规则优先

玩家应能理解失败原因。移动被挡、互动不可用、不能购买、招式不能使用、强制换人、训练师已击败、存档版本不兼容，都要有类型化原因，最终由表现层转换为可读提示。不能把规则失败隐藏在“模型回答了一段解释”或“按钮没有反应”里。

对战的视觉表现可以华丽，但实际结算只有一个权威来源。AI、UI、回放、日志、测试和存档都从同一份规则事件读取。不要为动画、模型说明或即时预览复制另一套伤害计算和胜负判断。

### 3. 内容优先

世界不会靠无限随机生成获得质量。正式内容应该由版本化内容包定义：地图、连接、出生点、物件、遭遇区、训练师、NPC、脚本、文本、商店、奖励和资源引用都有稳定 ID。AI 只能加速制作与变体探索，不能消除内容设计和审阅。

小而完整的区域优于大而空的地图。首个正式区域应该有足够的空间来证明系统，而不是证明地图生成能一次铺出很多格子。最少应存在起始点、可重复对话 NPC、一次性赠送 NPC、训练师、商人或治疗点、路线、草丛、至少一段跨图连接和一个可保存的返回点。

### 4. AI 可解释

AI 对战需要能说明“它在什么观察下提交了什么合法动作”，而不是暴露模型内部思维。系统记录输入摘要、可选动作、实际动作、模型/策略版本、延迟、回退原因和最终战斗事件。玩家层面的提示可以简短，例如“对手正在思考”或“对手采取了保守策略”；开发与质量环境应可导出完整审计记录。

AI 创作需要能说明“该候选从哪一版模板和内容上下文得到，经过哪些校验，谁批准了它”。原始提示可能包含敏感文本或版权风险内容，因此审计记录应保存必要摘要和哈希，不默认公开完整上下文。

## 内容范围：前 386 种宝可梦

本提案把全国图鉴第 1 至 386 号作为可出现在游戏中的物种范围。这个范围与当前 `game-data` 的嵌入图鉴边界一致。它带来清晰的资产、内容和数值上限，但不代表所有 386 种必须在第一版可捕获，也不代表每个形态、招式、特性和道具都自动进入产品。

内容范围应被分成四层：

| 层级 | 含义 | 例子 | 首发是否必须完整 |
| --- | --- | --- | --- |
| 物种允许集 | 可以被内容引用的物种 ID | 1 至 386 号的原始物种 | 是。引用验证必须完整。 |
| 可遇见集 | 当前发行内容实际可遭遇、获得或由训练师使用的物种 | 首区域的野生表和训练师队伍 | 否。逐区域扩展。 |
| 可战斗集 | 已为当前规则包实现、测试并允许进入对战的物种/招式/能力组合 | 规则包 MVP 覆盖的组合 | 否。必须明确拒绝未支持组合。 |
| 表现集 | 已有合法展示资源、名称、图鉴说明与 UI 占位的内容 | 菜单、战斗精灵、图鉴卡 | 否。可使用合法占位，但不得伪称完成。 |

这样处理可以避免两个常见错误。第一，不因为图鉴数据完整就让未实现的招式或能力进入战斗。第二，不因为战斗规则能表达某个物种，就假设它已有合法资源、地区来源和剧情用途。

## 规则范围与内容范围分离

“使用最新世代的对战引擎”在产品讨论中具有吸引力，但不能直接成为工程任务。现代对战规则包含多个彼此耦合的选择：招式分类、属性表、能力、携带道具、天气、场地、替换、先制、异常、命中、暴击、经验、特性、太晶化或其他世代机制，以及单双打格式。前 386 种内容并不能替这些选择作答。

因此产品应承诺的是“有一个明示版本的现代化规则包”，而不是“总是跟随最新”。每个可发行版本选择一个 `BattleRulesetId` 和修订号。该规则包说明：

- 参考目标和固定日期；
- 支持的对战格式；
- 支持或禁用的世代机制；
- 对前 386 内容的允许、替换、禁用和补充规则；
- 数据来源与许可证记录；
- 与前一版本的差异、迁移和存档影响；
- 可执行测试用例与已知未支持清单。

详细设计见 [对战规则包与前 386 数据](002-对战规则包与前386数据.md)。

## 角色与权限

产品中至少存在五种角色，不应混为“用户”。

| 角色 | 能做什么 | 不能做什么 | 主要入口 |
| --- | --- | --- | --- |
| 玩家 | 移动、交互、选择合法战斗动作、管理自己的存档 | 改写规则、绕过事件条件、读取隐藏信息 | 游戏 UI。 |
| 对战策略 | 在给定观察与动作集中选择一个动作 | 改写对战、读取对手隐藏数据、访问文件 | AI adapter / `OpponentPolicy`。 |
| 内容作者 | 编辑草案地图、NPC、训练师、文本与测试场景 | 直接污染已发布内容包 | 编辑器与内容工作台。 |
| 内容审阅者 | 批准、拒绝或退回候选；选择发布版本 | 让未通过校验的候选自动上线 | 审阅工作流。 |
| 发行维护者 | 冻结规则包、签署内容 manifest、发布迁移 | 通过 runtime 临时改写玩家存档 | 发行工具。 |

模型不应成为第六种拥有特殊权限的角色。它只能在“对战策略”或“内容作者的助手”这两个既有角色中工作，并继承相应的最小权限。

## 目标架构视图

未来架构应延续当前由外向内的依赖方向，而不是新建一个“AI 核心层”。AI 是外部能力，和文件、窗口、网络一样位于边界。下面是目标关系，不是现状 crate 清单：

```text
runtime / editor / model adapter
        |
        v
application orchestration
  - game product session
  - battle session bridge
  - content candidate validation workflow
        |
        v
domain / pure application state
  - battle ruleset and battle state
  - world and event state
  - content schemas and semantic validators
        |
        v
foundation values
  - IDs, diagnostics, deterministic inputs, serialization primitives
```

模型 provider 位于 runtime 或 adapter。它把请求变成 `AiDecisionRequest` 或 `ContentCandidateRequest`，把响应变成受长度和 schema 限制的值。应用层再决定是否把该值转换为某个合法动作或候选文档。即使 provider 返回结构正确的 JSON，也不能直接信任其业务语义。

## 一个正式游戏会话

当前存在 `game-session` 的运行时会话和 `game-foundation` 的纯薄切片状态，两者各自有价值。终态不能长期让二者各自拥有玩家队伍、战斗开始条件和战斗结果语义。未来需要一个产品会话聚合或明确的应用服务，其职责是编排但不复制下层规则。

它至少需要处理以下输入类别：

| 输入 | 进入哪一层 | 权威结果 |
| --- | --- | --- |
| 玩家移动/面对/交互 | 世界与事件应用服务 | 世界事件、可开始的交互或战斗请求。 |
| 世界 tick | 行为/事件调度器 | 受限 NPC 状态变化和可见事件。 |
| 遭遇随机输入 | 随机端口的冻结值 | 特定遭遇候选或未遭遇。 |
| 玩家战斗动作 | `BattleSession` | 战斗事件、回放步骤、阶段变化。 |
| 对手战斗动作 | 策略端口输出后再校验 | 与玩家相同的合法动作提交。 |
| 战斗结束 | 战斗结果映射器 | 对队伍、奖励、训练师和世界事件的原子补丁。 |
| 保存/加载 | 存档 adapter | 已校验的 `GameState` 或结构化失败。 |

该会话不应把实际 `Battle` 序列化成一个无法演进的大对象，也不应丢掉已经发生的回合事实。正确方向是在战斗生命周期中明确区分：可持久的开战快照、规则包版本、随机状态、双方输入、事件日志、当前阶段、结果补丁和表现回放位置。具体格式应在真实战斗桥接设计中决定。

## 最小正式区域

首个正式区域是工程验收工具，而不仅是内容。建议以一座小镇和相邻路线为单位，并给每个元素设定系统责任：

| 元素 | 玩家用途 | 系统验收用途 |
| --- | --- | --- |
| 起始屋或研究所 | 开始游戏、领取初始队伍 | 新游戏、一次性奖励、flag、队伍创建。 |
| 可重复对话 NPC | 获取提示或世界观 | 交互定位、条件对白、文本资产。 |
| 巡逻 NPC | 制造路线节奏 | 行为脚本、阻挡、碰撞、逻辑 tick。 |
| 商人或治疗点 | 管理资源 | 背包、金钱、商店或恢复命令。 |
| 路线与草丛 | 进入探索/遭遇循环 | 地图连接、遭遇表、随机输入、战斗进入。 |
| 训练师 | 提供挑战与奖励 | 视线/交互触发、真实战斗、一次性完成状态。 |
| 返回点和存档点 | 暂停与续玩 | 存档版本、重载、错误恢复。 |

首个区域不追求完整城镇美术。它追求所有关键状态变化都能从玩家操作开始、在纯测试中重演、在原生 host 中实际操作，并在编辑器中看见对应内容。

## AI 对玩家体验的边界

### AI 对战

玩家看到的是行为自然的对手，而不是模型输出。AI 可以有不同人格，例如保守、进攻、换人倾向、天气倾向或难度档，但人格必须最终映射为公开策略参数或训练师内容，不能通过隐藏读取改变规则。对手的思考时间应有上限；超时使用确定性后备策略；网络失败不弹出技术错误打断战斗。

### AI NPC

NPC 分为静态与动态两类。静态 NPC 的定义、能力、关键剧情、固定对白、训练师队伍与执行器归 Rust 和版本化内容包。动态 NPC 的下一段行为/对白由本地模型在闲时或明确触发窗口生成 DSL，再由 Rust 编译、校验、模拟并原子激活。玩家看到的是一致角色和可预测任务结果，而不是每次按键都进入无约束聊天。

“动态归模型”不等于模型拥有游戏状态写权限。模型可以读取被授予的公开事实槽位，例如区域、当前阶段、已完成事件和角色记忆摘要，并提出新的受限事件程序或预制文本。它不能承诺不存在的奖励、暗示未实现功能、泄露隐藏状态，或生成超出年龄分级与内容政策的文本。Rust 执行已激活的 DSL；任何副作用仍由事件运行时的类型化规则决定。

### AI 地图

玩家不应该区分一张地图是否由 AI 草案开始。每张已发布地图都必须通过同一套可达性、碰撞、连接、资源和事件检查。AI 生成的价值在开发期，不应使正式地图变成不可重现的在线随机结果。

## 范围切割

把范围切得足够明确，是避免项目被“能接 AI”吞没的关键。

### 第一版必须有

- 一条完整单人垂直切片，使用实际战斗会话而不是结果摘要替代。
- 一个冻结规则包和前 386 物种过滤。
- 单打、回合制、可回放的战斗；至少能覆盖首区域内容所需的招式和能力。
- 有限地图区域、可编辑内容包、NPC 与训练师。
- 本地存档、内容版本检查、失败恢复和基础迁移策略。
- 规则型对手 AI；模型 AI 可以是实验开关，但不能是唯一对手。
- AI 地图和 NPC 的开发期候选工作流，含审阅和导出。

### 第一版明确不做

- 联机 PvP、交易、交换、排行榜、账号系统和反作弊。
- 双打、多重战斗、完整竞赛系统、通信进化或跨设备同步。
- 面向玩家的无约束地图生成、无约束 NPC 聊天和即时修改规则。
- 一次性覆盖前 386 种的完整可捕获分布、完整招式表、美术和图鉴文本。
- 把任何特定模型供应商当作核心产品依赖。

### 后续可选扩展

- 第二个或第三个区域、地区级世界图和更复杂的任务系统。
- 有记忆但受事件状态约束的角色表达系统。
- 多种 AI 难度、离线小模型、策略训练与对局回放分析。
- 经过独立设计的玩家创作内容包交换，但前提是内容签名、审核、版本兼容和权利流程已经就绪。

## 风险与反模式

### 反模式：先接模型，再补规则

这会产生一个看似可玩的 demo：模型输出“使用十万伏特”，外层把它变成字符串，界面播放动画。但当 PP、替换、强制换人、隐藏信息、网络失败和存档恢复出现时，字符串路径没有可验证合同。正确做法是先冻结观察和动作，再让模型成为某个动作选择器。

### 反模式：把 AI 生成当作内容发布

模型生成一张 JSON 地图并不等于它可到达、可渲染、资源合法、事件可完成或适合产品。候选与发布之间必须有校验、模拟、人工审阅和 manifest。任何绕过这条链路的便利入口都将成为不可追踪的内容污染源。

### 反模式：把现代规则当成单个布尔开关

“使用新世代规则”不是一个 feature flag。它是很多机制、数据版本和边缘案例的组合。必须用可查询的能力矩阵表达支持范围，并允许未实现组合在内容导入阶段被拒绝。

### 反模式：用 UI 状态代替游戏状态

菜单或对白窗口关闭后，玩家是否已领取物品、训练师是否已失败、战斗是否已结束，不能由 UI 判断。UI 是投影。它可以丢失、重建或换平台；游戏状态必须独立保存并验证。

## 完成定义

产品终态不是“模型已经接上”。第一阶段产品完成时至少满足：

1. 从新游戏到存档加载的完整流程在不联网条件下稳定运行。
2. 所有参与战斗的规则都能由固定规则包、数据版本和测试样本解释。
3. 人类、启发式 AI 和模型 AI 只通过同一份可见观察与合法动作集合参与对战。
4. 一张已发布地图和一个已发布 NPC 都能追溯到版本化内容包、校验报告和审阅决定。
5. 发生崩溃、模型失败、内容版本不匹配或非法命令时，玩家状态保持可恢复或得到明确拒绝，不发生静默损坏。

只有达到这些条件，项目才拥有可持续扩展到更多地区、物种、规则和 AI 功能的基础。
