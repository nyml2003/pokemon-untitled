# AI NPC 与叙事生成

> 分类：未来；起草：2026-07-21。
> 状态：内容与事件系统提案。当前叙事 DSL 只实现了最小 actor 绑定脚本；本文不将目标事件语言误称为现有功能。

## 结论

NPC 明确分工：静态内容归 Rust；动态内容归模型。静态内容包含空间实体、能力边界、关键剧情、奖励、战斗、商店、任务 flag、持久化结构、DSL 执行器和固定文本。动态内容是模型基于已授予事实生成的下一版 NPC DSL、预制对白和行为变体。静态与动态必须使用同一套 DSL 语法、AST、编译器、CPS/EventProgram 中间表示、执行器、continuation 和场景测试；模型不直接扮演角色，也不直接执行输出；Rust 负责把候选编译、验证、模拟、冻结和执行。

这使 NPC 可以随世界进度发生真实变化，而不退化成随机启发式。动态不是“每次对话重新抽一句”，而是“在确定的生成窗口产出可审阅、可回放、可持久化的程序版本”。候选未通过或模型不可用时，NPC 保留上一版已激活 DSL。静态脚本与动态修订的差别只在来源和 `CapabilityProfile`：profile 限定该 NPC 可读取的事实、可调用的 DSL 指令、可写的状态集合和资源引用范围；它不改变语言语义，也不允许模型拥有独立执行器。一个 NPC 仍由空间实体、交互入口、行为状态、可选能力和文本资产组合而成；`Trainer`、`Merchant`、`Healer`、`Gift`、`Guide`、`Blocker` 等是可组合能力，不是一个不断膨胀的 `NpcKind` 枚举。

## 当前依据

当前代码已经展示了正确的分离方向：

- `world-domain` 的 `WorldActor` 表示位置、朝向、阻挡和移动；玩家与 NPC 命令分开，NPC 移动不会触发草丛遭遇。
- `world-application` 将地图 actor 投影为可渲染观察，并维护外观、NPC 脚本 continuation 与对白。它能按逻辑 tick 执行 actor 绑定的 CPS 脚本。
- `narrative-token`、`narrative-compiler`、`narrative-cps` 已实现一个最小 DSL：移动、转向、说话、等待和结束；脚本可绑定 actor，并有基本诊断。
- `game-foundation` 已把 NPC 定义成 actor 加 capability。礼物、训练师和商人可以组合；训练师目录已独立保存姓名、队伍和交互脚本，并可被纯命令编辑。
- `game-ramus-adapter` 已将 NPC 交互、移动、warp、遭遇、战斗结果、购买和存档路由为类型化 intent，但它不是运行期事件解释器。

当前缺失的是统一正式事件运行时、面对确认键的交互定位、条件分支、变量/flag 操作、通用副作用、实际世界与 `game-foundation` 的状态收敛、NPC 动态状态持久化和内容包集成。后续设计必须把这些空白补在 application/domain 的确定性边界，而不是交给模型“临场决定”。

## NPC 的正式模型

未来每个 NPC 定义应由稳定 ID 索引，并分为静态定义与动态状态。

```text
NpcDefinition (static content)
  identity
    - npc_id, display key, tags
  actor
    - map/region, initial position, facing, appearance, collision
  interaction
    - interaction entry event, facing/adjacency policy, priority
  behavior
    - idle, patrol, route, look-at, conditional visibility
  capabilities
    - trainer, merchant, healer, gift, guide, blocker, quest hook
  narrative
    - dialogue keys, persona profile, localization references

NpcState (dynamic save state)
  - current position/facing/behavior continuation
  - visibility/enabled state
  - current event continuation
  - claimed/repeatable counters
  - trainer defeated/rebattle state
  - durable relationship or quest flags where explicitly designed
```

静态定义绝不复制进每个存档；动态状态也不应把完整对话脚本、头像路径或训练师队伍复制进去。内容包升级时，加载器使用稳定 ID 将旧状态与新定义对齐；找不到定义或迁移规则时拒绝/迁移，而不是忽略 NPC 状态。

## 交互不是“选择一个 NPC ID”

当前薄切片可以用 `GameCommand::Interact { npc }` 验证能力组合，但正式玩家输入不能信任 UI 任意传入的 NPC ID。世界交互应从玩家位置、朝向、范围、遮挡和优先级计算一个或零个可交互目标。

建议采用两阶段流程：

```text
玩家按确认键
  -> WorldInteractionResolver 查找正前方/相邻对象
  -> 返回 InteractionTarget 或明确的 NoTarget/Blocked/Unavailable
  -> EventRuntime 从目标的入口事件创建 event session
  -> 事件按状态和内容执行一步
  -> GameState 获得事件结果补丁与可见事件
```

这使得 UI 无需理解 NPC capability，也防止 AI/脚本通过任意 ID 远程领取礼物。测试应覆盖：面向错误方向、距离过远、被障碍隔开、NPC 被隐藏、训练师已击败、礼物已领取、同格多对象优先级和等待中的事件不能重入。

## 事件运行时

事件运行时是未来 NPC 系统的核心，不是脚本播放器的附属。它接收静态事件程序、动态事件状态、当前游戏状态和一个明确命令，返回新的状态、事件和可能的“等待输入”。它不读文件、不调用模型、不直接渲染窗口。

第一版事件指令应小而完整：

| 指令 | 作用 | 状态边界 |
| --- | --- | --- |
| `Say` | 显示文本 key 或受限文本片段 | 表现等待；不修改长期状态。 |
| `Choose` | 在有限选项中等待玩家选择 | 输入验证；选择 ID 进入续体。 |
| `IfFlag` / `IfValue` | 条件跳转 | 只读已声明状态。 |
| `SetFlag` / `SetValue` | 写入已声明 flag/变量 | 原子更新游戏事件状态。 |
| `GiveItem` / `TakeItem` | 背包变更 | 复用库存与容量规则。 |
| `AddMoney` / `SpendMoney` | 经济变更 | 复用 `Money` 边界。 |
| `Warp` | 请求合法地图转换 | 由世界/内容服务校验。 |
| `StartBattle` | 建立真实战斗请求 | 由战斗桥接创建会话。 |
| `HealParty` | 按明确规则恢复队伍 | 由队伍状态服务校验。 |
| `MoveActor` / `FaceActor` | 请求 NPC 行为变化 | 复用 world actor 规则。 |
| `End` | 正常完成 | 清理临时 event session。 |

每条指令都有前置条件、成功事件、失败错误和续体规则。例如 `GiveItem` 在背包满时不能静默丢失物品，也不能先写 flag 再失败；它应保持原状态并让脚本走一个可选失败分支或返回 `InventoryFull`。`StartBattle` 不能在已有活动战斗时再开始；战后续体只能在真实 `BattleResultPatch` 返回后恢复。

不要一开始加入循环、任意表达式、文件访问、网络调用或动态代码执行。事件 DSL 的价值是作者可以推理和测试。复杂行为应先由新的、命名明确的领域操作表达，再决定是否需要变成脚本指令。

## 条件与变量

flag 和变量是强大但危险的全局状态。建议分层：

| 类型 | 用途 | 例子 | 不应承载 |
| --- | --- | --- | --- |
| 事件 flag | 离散、可审计的永久事实 | `professor-gift-claimed` | 任意数字或 UI 状态。 |
| 任务变量 | 有范围的枚举/整数进度 | 某任务阶段、计数 | 地图 tile 或自由文本。 |
| NPC 局部状态 | 单 NPC 的行为/关系 | 巡逻节点、重复对话阶段 | 跨区域主线事实。 |
| 会话瞬态 | 当前对白页、选择等待、动画 | 当前选项索引 | 存档长期结果。 |

所有 flag/变量在内容包中预声明类型、默认值、范围、可写事件和迁移策略。AI 不能发明一个字符串 flag 并希望运行时接受。内容校验器要建立读写图：找出从未定义的 flag、永不写入的条件、死分支、互相矛盾的条件和无限循环风险。

## AI 在 NPC 创作中的角色

AI 可以做四类工作，但每类输出都有不同合同。

### 角色提案

输入是区域主题、游戏进度、已有角色关系、可用能力、年龄分级和文本风格约束。输出是角色目的、可见行为、互动条件、潜在能力、对话槽位和与地图的关系。它不直接创建 `NpcDefinition`，而是输出供作者选择的结构化草案。

### 对话草案

输入是稳定文本 key、角色 persona、允许事实槽位、当前事件阶段、语言/本地化约束和最大长度。输出是一个或多个预制文本候选及其 DSL 引用。文本进入资产审阅和内容包，不直接写入存档或规则。模型生成后，玩家实际看到的是已激活 DSL 引用的预制文本，不是在按键时由模型临时自由生成的回答。

### 事件草案

输入是可用的指令白名单、已声明 flag/变量、目标体验和已知内容 ID。输出是受限事件 AST/DSL。编译器、类型检查器、状态分析器和模拟器决定其是否可执行。模型不能绕过白名单生成 `exec`、HTTP、任意脚本或不存在的道具/地图。

### 审阅辅助

模型可阅读结构化诊断，提出“这个分支可能不可达”“礼物 flag 先写会导致失败”等建议。它不能标记通过、不能修改批准状态，也不能声称验证已经完成。

## 人格与事实分离

角色人格是内容，不是权限。建议 `NpcPersonaProfile` 或等价数据只包含语气、主题、词汇限制、情绪标签、可谈论话题、禁谈话题和文本长度。能力、奖励、剧情条件、战斗队伍、商店货物和地图权限另存为业务定义。

这条分离对动态模型尤为重要。若把“我是慷慨的教授”直接解释为模型可赠送任意物品，模型会越过经济与任务规则。正确做法是模型只提出一段包含既有 `GiveItem`、条件与文本 key 的 DSL 候选；事件运行时在激活后才决定本次能否赠送 starter 和 potion，奖励是否成功仍由库存/flag/队伍规则决定。

## 动态 DSL 生成与激活

动态 NPC 不在每个玩家输入上请求模型。模型由闲时调度器或受控事件触发，例如区域加载完成、玩家到达新的任务阶段、NPC 当前脚本自然结束、或作者在编辑器中请求新的变体。调度器把一份有限的事实快照交给本地模型，得到候选 DSL 和预制文本，再交给 Rust 管线：

```text
已激活 NPC DSL + 允许事实快照
  -> 本地模型生成候选 DSL / 文本
  -> schema、名称空间、类型与能力检查
  -> 编译为 CPS / EventProgram
  -> 静态控制流与读写集合分析
  -> 在克隆 GameState 上模拟
  -> 生成内容版本与校验哈希
  -> 原子激活，或保留上一版本并记录诊断
```

激活点必须是明确的安全点：没有未提交的副作用、没有等待玩家选择的半截事件、没有进行中战斗、存档事务未打开。若候选改变后续行为，存档写入候选版本 ID 和已执行 DSL 的 continuation；加载时使用同版本内容或执行定义好的迁移。模型生成失败、超时、输出不合法或模拟不通过时，不回滚已完成剧情，也不把 NPC 置空，而是继续执行前一已激活版本。

模型输入只包含已授权事实：NPC 自己的状态摘要、已公开 flag、区域标签、允许能力、文本风格、可用内容 ID、生成预算和目标。它不读取整个玩家存档、其他未公开角色、内部随机状态、文件系统或密钥。动态性来自同一 DSL 的新版本，不来自越权读取或第二套语言语义。

## 训练师 NPC

训练师是 NPC 能力的一个消费者，也是 AI 对战内容的入口。训练师定义应引用：训练师 profile、队伍、规则包、奖励、战斗场景、AI 策略 profile、触发条件、失败/重战规则和战后事件入口。它不应把这些字段都塞进地图 actor。

训练师对战流程建议如下：

```text
玩家触发训练师入口
  -> 检查训练师动态状态与前置 flag
  -> 创建 BattleStartRequest
       player party snapshot + trainer roster + ruleset + seed + AI profile
  -> BattleSession 运行至结束
  -> 构造 BattleResultPatch
  -> 原子更新队伍、奖励、训练师状态、事件 continuation
  -> 执行战后脚本或返回世界
```

模型 AI 只存在于 `AI profile -> 动作选择` 这一段。它不能决定训练师是否已经败北、奖励多少、是否触发剧情或能否重复挑战。训练师编辑器在保存时校验队伍对规则包合法，AI profile 对权限和预算合法，文本/事件引用存在。

## 动态行为与调度

当前 `WorldApplication::advance_npcs` 以逻辑 tick 推进最小脚本。这个原则应保留：真实时钟属于 runtime，行为状态机只接收离散 tick 或明确事件。未来可扩展行为：

- 静止与定向；
- 固定路线巡逻；
- 看到玩家后转向或发起训练师事件；
- 条件出现/隐藏；
- 跟随或护送；
- 事件临时接管移动；
- 战后改变位置或对白；
- 区域加载/卸载时保存/恢复局部状态。

行为冲突需要确定性优先级。例如事件脚本移动优先于巡逻；战斗/对白时 actor 锁定；多 NPC 同时抢占格子按稳定 ID 或调度顺序仲裁；失败移动产生明确事件而不是无限重试。模型不得在每 tick 选择 NPC 移动，否则成本、重现性和调试都会失控。

## 内容编译与静态分析

NPC 内容包进入发行前至少应经历：

```text
JSON/YAML/编辑器项目
  -> schema 与 ID 校验
  -> narrative compile to CPS/event program
  -> type/permission checking
  -> flag/variable read-write analysis
  -> control-flow and termination checks
  -> reference validation against maps/items/trainers/ruleset
  -> scenario simulation
  -> localized text checks
  -> approved content artifact
```

静态分析应能报告：未绑定 actor、缺失 continuation、未知文本 key、未知物品、错误 namespace、从未可达分支、没有结束的事件、在失败后不可重试的赠送、已败训练师仍给奖励、warp 到不可走位置、需要不存在规则机制的战斗、不同事件同时写同一不可组合状态等。

不是所有叙事问题都能静态发现。语气、角色一致性、节奏、刻板印象和剧情质量需要人工审阅。AI 可以辅助标注，但不能替代负责的内容审阅。

## 场景测试

NPC/叙事测试应该以可读的场景文件或 Rust fixture 表达，而不是只截 UI 图。每个场景包含内容版本、初始游戏状态、世界位置、输入序列、随机输入、期望事件与最终状态。例如：

| 场景 | 输入 | 必须断言 |
| --- | --- | --- |
| 初始赠送 | 面向教授并确认两次 | 只获得一次队伍与道具；flag 写入。 |
| 背包满 | 与赠送 NPC 交互 | 不写 claimed flag；给出可恢复错误/分支。 |
| 重复训练师 | 第二次面对训练师 | 不开始战斗或按内容定义重战；不重复奖励。 |
| 条件对白 | 设置某任务 flag 后交互 | 选择新的文本分支。 |
| 巡逻阻挡 | 在狭路上推进多个 tick | NPC 不穿墙、不重叠、不永久封死主线。 |
| 战后续体 | 赢得真实战斗后继续事件 | 队伍/奖励/训练师状态一致，脚本恢复正确。 |
| 存档恢复 | 对话/事件中保存或在安全点恢复 | 只恢复设计允许的状态；不复制瞬态 UI。 |

将场景测试纳入 `ops` 的质量入口之前，可以先保持在 crate 单测，但不要要求作者手工开窗口才能验收 NPC 逻辑。

## AI 生成的评估与审阅

AI NPC 草案应记录：请求版本、允许能力列表、引用内容版本、模型/模板标识、候选 AST/文本哈希、编译诊断、静态分析结果、模拟报告、人工审阅人和最终决定。这样当某个角色后来出现不一致奖励或文本问题时，可以追溯是合同缺陷、模型输出、作者编辑还是审阅遗漏。

采纳率、手工修改密度、编译失败率、未通过语义检查率、重复文本率、人物设定冲突数和试玩问题数都可以帮助改进提示与模板。但所有指标都不能自动把“最像样的文本”批准为正式剧情。

## 实现阶段

### N1：交互解析与静态 NPC 合同

在不接 AI、不扩展 DSL 的前提下，定义玩家面对确认键如何解析目标，收敛 `game-foundation` actor 与 `world-application` actor 的 ID/位置边界。退出条件是玩家无法用任意 ID 远程交互，且基本静止 NPC、阻挡 NPC 和重复对话 NPC 都有纯测试。

### N2：最小事件运行时

实现 `Say`、等待确认、条件 flag、设置 flag、赠送物品、warp、开始战斗和结束。复用背包、金钱、世界和战斗桥接的业务规则。退出条件是薄切片不再依赖摘要式 ad hoc 流程，而是通过事件 program 完成；失败不部分修改状态。

### N3：内容化训练师与战后续体

让训练师 NPC 从内容包引用真实战斗和 AI profile，战后结果恢复事件 continuation。退出条件是胜利、失败、逃跑/不可逃跑、重复挑战和存档恢复都有场景测试。

### N4：行为状态与跨图持久化

扩展巡逻、出现/隐藏、局部状态和地图加载边界。退出条件是逻辑 tick 可重现，跨图/重载不丢失或复制 NPC，行为冲突有稳定仲裁。

### N5：本地模型生成动态 DSL

定义动态 NPC 候选 schema、闲时调度器和安全激活点。模型生成预制文本和事件/行为 DSL，Rust 编译、分析、模拟并为候选签名。先只允许无奖励的路线引导和有限行为变体。退出条件是模型无法产生超出指令白名单的可执行内容，生成失败始终保留旧 DSL，且候选版本可在存档中重放。

### N6：动态 NPC 的内容发布与演进

将经过自动验证的动态 DSL 作为可审阅内容事件记录，可按项目策略自动激活或进入作者审批队列。扩大到受明确 flag 约束的任务旁支与训练师战后行为，但不允许模型拥有奖励/战斗/flag 的自由权限。退出条件是任何动态变化都有来源、输入摘要、DSL diff、模拟报告、激活点和回退版本，且运行时只执行 Rust 已验证的程序。

## 反模式

### 用一个 `NpcKind` 枚举堆所有行为

这样很快出现“会巡逻的商人、战后送礼的训练师、条件出现的引导者”等组合爆炸。应使用 actor、interaction、behavior、capability 和 state 的组合。只有真正互斥且规则不同的概念才使用枚举。

### 把自然语言当作事件语言

“玩家赢了就给药”不是可执行合同。需要明确胜负来源、库存容量、物品 ID、重复领取规则、失败分支和状态写入顺序。模型擅长把意图说得通顺，不擅长自动填补所有状态不变量。

### 让模型拥有奖励工具

若模型工具列表有 `give_item(name, amount)`，它就变成游戏规则入口。正确工具要么不存在，要么只接受事件运行时已经批准的单次受限效果 token。模型更适合生成文本和草案，不适合获得 stateful authority。

### 用真实时间驱动核心剧情

真实时间会使测试、回放、暂停和存档复杂。核心只应接收逻辑 tick、玩家输入和明确事件。runtime 可以决定多久给一个 tick；游戏状态不能读取系统时钟。

## 完成标准

AI NPC 与叙事生成 MVP 完成时，应达到：

1. NPC 的空间、交互、能力、文本和动态状态有明确分离，并使用稳定 ID 引用。
2. 交互目标由世界位置/朝向解析，不能由 UI 或模型任意指定。
3. 事件运行时的每种副作用都有类型化前置条件、事件、失败和原子状态语义。
4. 训练师对战进入真实 `BattleSession`，战后通过受验证结果补丁回写并恢复事件。
5. AI 只能生成结构化角色、预制文本和事件候选 DSL；所有候选经过编译、语义检查、模拟和按项目策略的审阅/自动激活。
6. 动态 NPC 在闲时或受控窗口由本地模型产生新 DSL，失败时保留旧版本；运行时只执行 Rust 已验证的程序，无直接状态写权限、无隐藏信息访问。
7. 关键 NPC 流程有可重放场景测试，并能在保存/加载后保持一致。

达到这些条件后，角色的丰富性才不会以牺牲故事确定性和存档可靠性为代价。
