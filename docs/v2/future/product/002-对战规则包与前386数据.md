# 对战规则包与前 386 数据

> 分类：未来；起草：2026-07-21。
> 状态：R0 已实现，后续规则与数据提案。当前 `battle-domain` 是第三世代风格的确定性实现；本文不宣称其已经支持现代规则。

## 结论

“前 386 种宝可梦”应当限制内容集合，“现代规则”应当作为一个版本化规则包限制战斗行为。两者不能互相代替。项目应先定义一个可冻结、可查询、可测试、可迁移的 `BattleRuleset` 合同，再把当前第三世代风格的 `battle-domain` 逐步演进或在明确边界内替换为规则包执行器。

不要追逐一个会不断变化的“最新世代引擎”。对每一个发行版本，选择一个明确的规则参考目标和修订号。若将来要升级，只能新建规则包并提供兼容策略，不修改已发行存档和回放所依赖的旧规则含义。

### R0 实现事实（2026-07-22）

当前 workspace 已有纯 `battle-ruleset` crate，冻结 `legacy-gen3@1`。它校验原始默认形态、`1..=386` 种族范围、当前 `battle-domain` 的属性/能力/招式效果映射与学习表；`ProductSession` 在建立、恢复和构造真实产品队伍时都使用它。首区域实际使用 `Treecko`、`Torchic` 和 `Bulbasaur`，而带现代 `fairy` 属性的 `Ralts` 会被明确拒绝。

规则引用通过 `BattleStartRequest`、`BattleResultPatch` 和产品 `SaveEnvelope` 传播；`ProductSession::from_save` 会拒绝缺失或不匹配的规则引用。`BattleRuleset::replay` 可重放固定队伍、种子和 `BattleCommand` 序列。R0 只保证这些已实现的能力，不将前386数据错误地等同于全量可战斗内容。

## 当前依据与差距

当前代码已经提供了重要基础：

- `battle-domain` 以 `Battle` 为聚合根，确定性持有两支六人队伍、当前出战、待提交命令、伪随机状态、天气、回合和事件历史。
- `Battle::legal_actions` 是动作可用性的权威查询。`Battle::submit` 在候选状态上校验和结算；失败不会部分修改状态或事件历史。
- `battle-application` 已按视角生成观察，并能隐藏对手未公开信息；`battle-session` 已把对手策略、玩家动作、回放和强制替换编排为交互生命周期。
- `game-data` 的嵌入图鉴覆盖全国图鉴第 1 至 386 号，并有经导入校验的数据集。数据集含有宝可梦、能力、属性、招式和学习表等记录。
- `game-foundation` 已保存队伍的简化 HP、PP、经验和战斗结果，但它目前接收的是摘要 `ResolveBattle`，不是完整的 `Battle` 执行结果。

这些能力并不等于“现代规则完成”。当前 `battle-domain` 的公开文档明确定位为第三世代风格；现有类型和效果只覆盖已写入的规则。`game-data` 有数据也不表示每个数据条目可被当前状态机执行。因此演进必须从“支持矩阵”开始，而不是先批量导入更大数据表。

## 规则包的定义

规则包是一次战斗所需的不可变业务配置与可执行行为版本。概念上它包含以下部分：

```text
BattleRuleset
  identity
    - ruleset_id
    - revision
    - reference_target
    - effective_date
  format
    - single / double / other
    - level policy
    - team-size policy
    - clauses
  mechanics
    - type chart revision
    - move category revision
    - status, critical, accuracy, priority rules
    - ability, item, weather, terrain and field rules
    - generation mechanics switches
  content policy
    - allowed species/forms/moves/abilities/items
    - replacement or prohibition table
    - learnset and legality policy
  random policy
    - PRNG algorithm and seed format
    - random draw ordering
  compatibility
    - save/replay version requirements
    - migration or explicit rejection policy
  verification
    - executable cases, corpus hashes, known gaps
```

`reference_target` 不是一段营销语言。它应记录来源名称、固定版本/日期、许可审查状态和内部差异说明。项目不需要在领域代码中嵌入网页链接，但发布资料必须能追溯“为何某条规则是这样”。若资料无法合法使用或无法稳定引用，则该资料不能成为发行规则的唯一依据。

## 为什么不能使用一个“最新”常量

把规则包命名为 `latest` 会损害三件事。

第一，回放失去含义。两个月前发生的战斗若按今天的新规则重放，事件可能不同。第二，存档失去稳定性。进行中的战斗、携带道具和学习表可能在无迁移的情况下变得非法。第三，AI 基准失去可比性。昨天训练或提示出的策略在规则改变后不再是在同一问题上竞争。

因此代码和数据只能使用稳定 ID，例如 `ruleset:modern-singles-r1`，不能把规则查询写成“取最新配置”。发布渠道可以显示“当前推荐规则”，但它只是一个索引到固定版本的产品决定。

## 前 386 内容政策

前 386 是一个物种集合，不是完整的战斗合法性集合。规则包需要至少维护以下表：

| 表 | 主键 | 作用 | 失败时的行为 |
| --- | --- | --- | --- |
| 物种允许表 | `SpeciesId` | 限制可被内容引用的原始物种 | 内容导入拒绝。 |
| 形态表 | 物种 + form | 说明哪些形态能出现和如何命名 | 组队/导入拒绝。 |
| 招式可用表 | `MoveId` + 规则包 | 标注已实现、禁用、替代或待实现 | 战斗队伍构造拒绝。 |
| 能力可用表 | `AbilityId` + 规则包 | 标注执行状态与效果版本 | 队伍构造拒绝或使用明确替代。 |
| 道具可用表 | `ItemId` + 规则包 | 区分战斗道具、世界道具和未支持项 | 内容导入拒绝。 |
| 学习合法表 | 物种/形态 + 招式 + 来源 | 验证训练师和玩家队伍 | 编辑器给出诊断。 |
| 机制兼容表 | 物种/招式/能力 + 现代机制 | 处理条件机制和例外 | 规则编译或战前校验拒绝。 |

允许表必须是显式白名单，而不是“数据里有就允许”。早期 MVP 可以只允许几十只物种和有限招式，但未支持项要以可读诊断拒绝。这样内容作者不会误以为自己只是“碰到了一个引擎 bug”。

## 规则架构候选

当前 `battle-domain` 不是需要立刻推倒的错误实现。它已经证明了确定性、事件历史、原子提交和视角观察的方向。未来需要先做一次设计决策，比较三种方案。

| 方案 | 做法 | 优点 | 主要风险 | 推荐用途 |
| --- | --- | --- | --- | --- |
| A. 增量演进 | 在现有 `battle-domain` 中加入版本化规则数据和更多效果 | 最大化复用现有测试与事件模型 | 现有 Gen3 假设可能渗入大量分支 | 先做规则包 MVP 时优先评估。 |
| B. 内核与规则包拆分 | 提取通用回合调度，规则包提供静态表与效果解释 | 长期可支持多版本和模拟 | 抽象过早会造成难以验证的框架 | 当 A 的边界已清楚且第二规则包真实需要时。 |
| C. 外部引擎 adapter | 用外部模拟器做规则执行，本地保留会话和观察 | 可能更快获得规则覆盖 | 许可、版本、确定性、跨语言错误和事件语义难控 | 仅在来源、许可和可测试性充分确认后评估。 |

路线默认从 A 开始，但不承诺 A 必然终局。关键不是 crate 名称，而是以下边界不能丢失：规则执行必须可确定性测试；调用方只能提交合法动作；观察必须按视角过滤；事件顺序是可持久化事实；外部引擎若存在也只能成为一个 adapter，不能让核心会话依赖不可解释的进程输出。

## 规则包 API 原则

未来 API 不应把“世代”写成散布的整数判断。它应把问题表述为规则能力。例如：

```text
ruleset.supports_move(move_id)
ruleset.resolve_move(move_id) -> MoveDefinition | UnsupportedMove
ruleset.validate_team(team) -> diagnostics
ruleset.active_mechanics() -> MechanicsProfile
ruleset.new_battle(initial_state, random_source) -> Battle
ruleset.apply(action) -> events + next state
```

上面的名称只是示意，不要求直接按此命名。重要的是调用方不该在 UI、AI adapter 或内容导入器中写 `if generation >= ...`。所有“这个招式是否属于本版”“这个物种在本版能否使用这个能力”“某机制是否可选”的判断由规则包统一回答。

规则包也不能直接读取 JSON 文件、网络或系统时间。外层在加载内容时解析并校验规则数据，向纯核心传入已构造的不可变对象。这样测试能用小型 fixture 覆盖边缘规则，不必依赖整套正式数据。

## 现代化策略的阶段切分

“现代规则”应按战斗体验和数据依赖切，而不是按一代一代全量搬运。一个可执行的顺序如下。

### 阶段 R0：冻结当前基线

先把当前第三世代风格实现变成明确的 `legacy-gen3` 基线。完成以下工作：

- 给现有规则、类型表、伤害类别、能力效果和随机算法一个稳定内部版本标识。
- 为已有招式效果建立清单，记录“已支持、部分支持、未支持、测试覆盖”。
- 为当前 battle event 建立序列化或可比较快照 fixture，防止后续重构无意改变事件顺序。
- 建立一组最小对局：普通伤害、属性克制、PP 消耗、异常、天气、替换、强制替换、逃跑、胜负和非法动作。
- 明确当前 `Pokemon` 与 `Move` 构造器中哪些字段已经是规则输入，哪些只是展示或尚未接入。

退出条件不是“所有第三世代规则都完美”。退出条件是团队知道当前实现到底承诺什么，且能用测试保护它。

### 阶段 R1：现代单打核心

选择一个固定现代规则目标后，只实现首区域所需的单打子集。它通常包括：当前属性相性和物理/特殊分类策略、基础伤害公式、命中、优先级、替换、主要异常、基础能力、天气、道具边界和经验/奖励映射。是否包含现代专有机制必须单列决定，不应为了“现代”自动塞入。

R1 的内容策略要反过来限制地图和训练师：首个区域只使用已支持物种、招式、能力和道具。训练师编辑器在保存前执行规则包校验；地图/NPC 内容校验器检查训练师引用的规则包版本。

### 阶段 R2：深度与边缘机制

在真实对局、测试样本和内容需要驱动下扩展特性、道具、天气联动、状态细节、招式多目标或可选机制。每次扩展都必须同时完成：规则实现、数据许可表、事件语义、AI 观察更新、回放 reducer 更新、至少一个正例、一个边界例和一个非法输入例。

### 阶段 R3：规则包升级机制

只有已有一版稳定发行规则后，才研究第二规则包或升级。升级不是替换常量；它要产出差异表、回放版本策略、进行中战斗策略、队伍合法性重验、内容迁移和存档迁移。无法安全迁移时应明确拒绝加载旧存档或锁定在旧规则包，而不是静默改变结果。

## 数据供应链

当前 `game-data` 使用离线嵌入的、经校验的 PokeAPI 数据快照。未来规则系统需要把“原始百科数据”与“可执行规则数据”分开。

```text
上游数据快照
  -> 开发期导入与许可证记录
  -> 标准化的物种/招式/能力基础数据
  -> 规则包补充表与人工修订
  -> 规则包编译器/校验器
  -> 发行时嵌入或随内容包分发的不可变产物
```

上游数据可以告诉我们物种、招式或学习关系的候选事实，但不能自动解决规则解释、版本差异、中文显示、资源权利或产品平衡。规则包补充表必须是项目自己维护的版本化资产，并记录每项手工修订的理由和来源摘要。

导入阶段应输出至少四类诊断：

1. 源数据完整性：文件缺失、格式错误、版本不符、重复 ID、非法范围。
2. 规则可执行性：某招式有数据但没有效果实现；某能力被引用但不在允许表。
3. 内容合法性：训练师、遭遇表或初始队伍使用不支持组合。
4. 发行合规性：资源来源未记录、许可证状态未知、显示文本或资产缺失。

这些诊断必须带 ID、文件/逻辑位置、规则包版本和可行动建议。不要只返回“data invalid”。

## 随机性与回放

AI 对战和规则升级都会放大随机性处理的缺陷。规则包必须定义随机数契约：算法、状态大小、种子编码、每类决策的抽取顺序、范围映射和是否允许外部提供固定抽取值。随机数不是 UI 的便利函数，也不是模型 provider 的副产物。

推荐把随机使用视为可审计输入流：

```text
BattleStart
  ruleset_id + revision
  initial teams
  initial random state

BattleTurn
  player action
  opponent action
  consumed draws with purpose tags
  emitted events

BattleFinish
  outcome
  result patch
  final random state
```

实现不必在每次发布时持久化所有内部随机实现细节给玩家查看，但回放测试和缺陷报告必须能重建同一条流。若升级 PRNG，旧回放仍使用旧版本解释器，或明确标记不可重放；不能默认用新算法“近似重演”。

## 对战事件合同

`battle-domain` 已有有序事件模型。未来规则扩展应优先扩展事件，而不是让表现层从最终 HP 差异猜测发生了什么。每个新机制应回答：

- 触发前后的可观察状态是什么？
- 事件发生的顺序是什么？
- 哪些信息对对手隐藏，哪些在事件后公开？
- 回放 reducer 如何从事件重建表现步骤？
- 存档中的进行中战斗是否需要包含该事件或可从状态重算？
- AI 观察中何时出现该信息？

例如，一个能力触发不只是一段动画文本。它可能影响行动次序、伤害、状态、换人限制或天气。若没有事件语义，AI 训练数据、回放、日志和 UI 会分别得出不同解释。

## 从真实战斗到游戏状态补丁

`game-foundation` 的 `ResolveBattle { outcome, hp, pp }` 已完成薄切片价值，但不能成为最终桥接。未来需要一个 `BattleResultPatch` 或等价类型，它由真实战斗结束状态构造，并明确说明哪些字段可回写。

| 类别 | 来自战斗的事实 | 写入长期状态的规则 |
| --- | --- | --- |
| 队伍 | 当前 HP、PP、异常、经验、等级变化、昏厥 | 只更新参与者与合法受影响成员；必须通过队伍不变量。 |
| 战斗本身 | 胜负、逃跑、回合数、随机状态、规则包 | 作为日志/回放/审计事实；是否保留由存档策略决定。 |
| 世界 | 野生遭遇消耗、训练师已击败、可重战条件 | 只能由战斗来源和事件定义共同决定。 |
| 奖励 | 金钱、物品、flag、剧情推进 | 必须经过游戏事件规则，不能由 UI 或 AI 直接加。 |
| 表现 | 动画队列、音效、消息 | 不写入长期状态；重载后可以重新投影。 |

补丁构造失败时，原始战斗和长期状态都不能被半更新。应在应用服务中先验证映射，再原子提交到 `GameState`。若存档中途发生故障，重新加载应能恢复到战斗前检查点或完整的进行中战斗，而不是只剩一半奖励。

## 测试矩阵

规则包需要多层测试，而不是依赖手动对战。

| 层 | 目标 | 例子 |
| --- | --- | --- |
| 值对象 | ID、数值范围、队伍构造、数据解析 | 386 范围外物种、空招式、重复队员。 |
| 规则单元 | 独立伤害、属性、状态、能力、随机映射 | 克制倍率、PP 不足、异常阻止行动。 |
| 状态机 | 命令、回合、强制替换、事件序列 | 双方提交、非法换人、胜负结束。 |
| 观察 | 隐藏信息和合法动作过滤 | 对手未公开招式、强制替换阶段。 |
| 回放 | 事件 reducer 与最终快照一致 | 每个新增事件都能重播。 |
| 数据/内容 | 规则包允许表与训练师/遭遇表一致 | 未实现能力被内容引用时拒绝。 |
| 应用桥接 | 真实战斗结果到 `GameState` 的原子回写 | 训练师胜利只奖励一次。 |
| 回归语料 | 固定初始状态、种子、动作和期望事件 | 规则升级后比较差异。 |

回归语料应该存储业务输入与期望输出，不只存截图。每条用例要标注规则包 ID、案例目的、数据版本和来源类别。外部资料导出的案例还应保留足够的版权合规摘要，而不是大段复制受限文本。

## AI 对战对规则包的要求

AI 接入不能反过来决定规则。它只对规则包提出三个必要要求。

第一，合法动作要可枚举。模型不应凭自然语言猜哪些招式可用。第二，观察要可序列化且按视角过滤。模型不应接触隐私数据或内部随机状态。第三，动作提交要可验证并给出明确拒绝原因。模型的错误是正常输入错误，不是引擎崩溃原因。

对于策略研究，可额外提供“训练视角”或“全信息模拟视角”，但它必须是不同类型和不同权限，不可被在线对战策略误用。任何在全信息下训练的策略进入公平模式时，都只能接受公平模式观察。

## 内容编辑器对规则包的要求

编辑器应在作者最早能修复问题的时刻显示规则诊断。创建训练师队伍时检查物种、等级、招式、能力和道具；创建遭遇表时检查等级范围、权重、规则包允许集；创建 NPC 奖励时检查物品是否可用。导入或发布时再做全局校验，防止手工编辑绕过 UI。

编辑器不应该自行实现战斗规则。它向规则包查询显示数据和验证结果。这样 CLI、GUI、AI 生成器和发行校验器收到同一结论。

## 决策清单

在写现代规则实现之前，必须完成并记录以下选择：

1. 首发采用的对战格式是单打还是包含双打；队伍数与等级规范是什么。
2. “现代”参考目标是什么；该目标的固定版本/日期与资料来源如何记录。
3. 前 386 内容中允许哪些形态、招式、能力、道具；未支持项是禁止、替代还是延后。
4. 是否包含任何世代专有机制；若包含，它的资源、UI、AI 观察、存档和回放合同是什么。
5. 数据原始来源、转换步骤、许可状态和发行边界是什么。
6. 随机算法与回放格式是什么；规则升级如何兼容旧记录。
7. 规则包配置是随二进制嵌入、随内容包发布，还是两者结合；如何签名/校验。

这些不是实现细节。任何一项缺失都会使“规则完成”的定义模糊，最终将问题推迟到存档、AI 或发行阶段才爆发。

## 完成标准

规则包 MVP 完成时，应达到以下可验证状态：

- 有一个不可变规则包 ID 与修订号，并能在战斗、回放、内容包和存档中被引用。
- 前 386 物种范围通过导入与内容校验执行，不是文档约定。
- 首个正式区域使用的每个物种、招式、能力、道具和机制都在允许表中，且有测试覆盖。
- 给定初始状态、规则包、随机状态和动作序列，真实战斗能得到一致事件与最终状态。
- 从双方观察生成的合法动作集合能驱动人类 UI、规则型 AI 和模型 adapter。
- 未支持组合、规则/内容版本不匹配、非法队伍和无效动作都返回结构化诊断，且不会改变状态。

达到这些条件后，项目才应进入模型对战和大规模内容生成的正式实现阶段。
