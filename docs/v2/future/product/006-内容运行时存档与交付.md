# 内容运行时、存档与交付

> 分类：未来；起草：2026-07-21。
> 状态：产品集成与发行提案。当前 `game-foundation` 已验证纯薄切片存档；本文描述它与真实世界、真实战斗、内容包和动态 NPC DSL 收敛后的目标。

## 结论

未来产品需要一个统一的内容运行时合同：静态 Rust 内容、动态模型生成的 DSL、地图、NPC、训练师、规则包、资源和玩家存档都用版本化 manifest 连接。Rust 是最终执行与状态校验的权威；本地模型只为动态 NPC 或地图/NPC 创作产生候选内容。候选通过编译、模拟和策略检查后成为一个不可变内容修订，运行时只加载并执行该修订。

存档保存的不是模型会话、提示词或“下一次让模型继续想”。存档保存可重放的游戏状态、内容引用、规则包引用、活动会话以及动态 DSL 的已激活版本/continuation。模型不可用时，旧存档必须仍能加载并由 Rust 执行已冻结 DSL；模型再次可用时，只能在新的安全生成窗口提出下一版候选。

## 当前起点

当前工程存在两条需要收敛的路径：

- `game-session` 是当前原生游戏 host 的纯会话，拥有世界与 battle scene，并以 demo roster 和 `BattleSession` 驱动现实战斗交互与回放。
- `game-foundation` 是已被单元测试证明的产品薄切片，拥有静态内容、队伍/背包/金钱/flag/训练师状态、简化的战斗摘要、版本化 `SaveEnvelope` 和纯状态转换。
- `game-ramus-adapter` 已能把被授权的调用转换为 `GameCommand` 或保存意图，但不读写状态。
- 地图、世界和叙事各有当前项目/脚本模型；它们尚未成为 `game-foundation` 的正式内容包输入。

这不是要否定任一路径。`game-session` 已证明运行时、输入、场景投影和实际战斗；`game-foundation` 已证明长期状态、经济、NPC 能力和保存。未来需要把二者的职责合并为一条产品会话，而不是持续同步两份“玩家队伍”或让世界和薄切片各自认为自己拥有 battle result。

## 统一所有权

终态应将状态按寿命和权威拆开。

| 状态类别 | 例子 | 权威所有者 | 保存方式 | 模型是否可写 |
| --- | --- | --- | --- | --- |
| 静态 Rust/发行内容 | 规则实现、DSL 执行器、已发布地图、NPC 定义、资源索引 | 版本化内容包与二进制 | manifest 引用 | 否。模型只能生成候选。 |
| 动态已激活内容 | 某 NPC 的 DSL 修订、预制文本修订、可用行为变体 | 内容运行时的内容修订表 | 修订 ID + 必要 snapshot | 否。通过验证后由激活事务写入。 |
| 长期玩家状态 | 位置、队伍、背包、flag、训练师状态、NPC continuation | `GameState` 或等价产品聚合 | 存档 envelope | 否。只由类型化命令/事件修改。 |
| 进行中会话 | 对战阶段、事件等待选择、回放位置、当前地图加载 | 产品会话 | 安全点快照或可恢复日志 | 否。 |
| 外部能力状态 | 模型队列、请求重试、缓存、计费、窗口、网络 | adapter/runtime | 可丢弃诊断或本地缓存 | 模型 adapter 自身管理，但不进入规则状态。 |
| 派生表现 | UI 焦点、动画、声音、GPU 资源 | presentation/runtime | 不保存或仅保存用户设置 | 否。 |

这张表是动态 NPC 设计的底线。模型确实负责“动态内容”，但内容要先从候选变成已激活修订；已激活修订随后与静态内容一样由 Rust 解释。这样模型退出、更新、换模型或清空缓存不会改变正在进行的世界事实。

## 内容包

内容包不是一个任意资产目录。它是可加载、可验证、可引用、可签署和可回滚的发行单元。第一版可以使用简单目录和 JSON/二进制文件，不要求先实现复杂包管理器；但 manifest 应从一开始存在。

概念结构：

```text
content-package/
  manifest
    package id, revision, compatibility range, content hash
    ruleset reference, data reference, locale/resource references
  maps/
    map projects, world topology, encounter definitions
  npcs/
    static NPC definitions, actor behavior defaults, dynamic DSL base versions
  events/
    compiled event programs and source maps
  trainers/
    trainer profiles, teams, AI policy profiles
  data/
    item, reward, shop, species filtering and balancing tables
  texts/
    localized pre-generated text assets
  dynamic/
    approved/activated generated DSL revisions and provenance manifests
  tests/
    content scenarios, reachability expectations, battle fixtures
```

具体物理布局可调整，但 manifest 必须能回答：该包依赖哪个对战规则包、哪个基础数据快照、哪些资源、哪些动态 DSL 修订、是否可用于某个存档、是否覆盖另一个包、以及完整性如何验证。

内容包内部不接受“运行时再从网络拿一个脚本”。所有可执行 DSL 在打包时编译，或者在本地生成后经 Rust 编译并写入候选/激活修订。运行时加载错误应产生结构化 `ContentLoadError`，不应悄悄省略 NPC 或用空地图继续。

## 静态内容与动态 DSL 的组合

每个动态 NPC 至少有一个静态基线 DSL，由 Rust 内容包提供。基线定义角色不论模型是否可用都具备的最低行为：站位、基本对话、能力限制、失败时的路径和可恢复终止。模型生成的是受限 patch 或后继修订，而不是完整替换整个人物的任意程序。

建议将动态修订表示为：

```text
DynamicNpcRevision
  npc_id
  base_revision
  revision_id
  declared input facts schema
  generated DSL source
  compiled program hash
  pre-generated text asset hashes
  read set / write set
  simulation report
  activation policy and timestamp/logical epoch
  provenance summary
```

`read set` 和 `write set` 是关键。模型候选只能读取声明的公开事实；写集合只能包含该 NPC 已获授权的 flag、局部状态或事件效果。若候选写入一个未授权奖励 flag、访问其他 NPC 的私有状态、启动不兼容的战斗或引用未知资源，编译/语义检查必须拒绝。

动态修订的“版本”不一定都要提交到 Git。项目可定义两种生命周期：作者审批的正式内容修订进入内容包；单人游戏本地生成且自动验证通过的修订进入玩家本地动态内容仓，随存档或本地 profile 绑定。无论哪种，修订都要有稳定 ID、哈希、基线版本和可回退点。不能只保存模型输出文本。

## 动态 DSL 的安全生成窗口

模型可在闲时生成，不代表任意时刻都可改变 NPC。生成、验证和激活应分开。

| 阶段 | 可做什么 | 禁止做什么 |
| --- | --- | --- |
| 计划 | 调度器发现某 NPC 需要后继行为；收集允许事实 | 修改 `GameState` 或中断玩家输入。 |
| 生成 | 本地模型返回候选 DSL/文本 | 调用事件效果、打开存档、修改活动战斗。 |
| 验证 | Rust 编译、类型检查、静态分析、模拟 | 把候选当作已经生效。 |
| 挂起 | 候选等待安全点/审阅 | 覆盖正在等待选择的 continuation。 |
| 激活 | 原子写入动态内容修订并更新引用 | 跨越未完成事务或与旧 DSL 混合执行。 |
| 执行 | Rust 解释已激活 DSL | 再次询问模型决定单个指令。 |

安全点至少包括：当前 NPC 没有运行中的事件 continuation；玩家不在与该 NPC 的交互中；没有该 NPC 相关的进行中战斗；存档不在写入事务中；新修订能从已声明的状态入口开始。若新 DSL 需要替换一个已运行的后续阶段，应提供显式迁移 function 或让旧 DSL 先自然结束。绝不允许在一段 `GiveItem` 执行到一半时换脚本。

生成调度器属于 runtime/application 外壳。它可以在帧空闲、地图加载后、任务状态改变后或保存完成后运行，并受 CPU、内存、电池、玩家设置和模型预算控制。它不能决定游戏逻辑 tick，更不能把“模型想好了”当作强制玩家等待的理由。

## 产品会话收敛

未来可称为 `ProductSession`、`GameRuntimeState` 或其他名称，命名不是重点。它必须把世界、事件、战斗、长期状态和内容版本放到一个协调点，避免任何下层状态越过边界。

一次世界移动的目标流程：

```text
normalized input
  -> ProductSession validates scene and current content revision
  -> world reducer applies movement
  -> event/encounter resolver produces typed request
  -> session either remains in world or creates battle/event sub-session
  -> GameState commits durable patch only on success
  -> snapshot + typed events project to presentation
```

一次战斗结束的目标流程：

```text
BattleSession reaches Finished
  -> BattleResultMapper reads final battle state + ruleset + content reward rule
  -> constructs BattleResultPatch
  -> ProductSession validates patch against GameState and active event
  -> atomically commits party/world/reward/NPC changes
  -> resumes event continuation or world scene
  -> emits immutable result events for replay and UI
```

一次动态 NPC 激活的目标流程：

```text
idle scheduler selects eligible NPC
  -> local model produces candidate DSL
  -> Rust compiler/analyzers/simulator accept candidate
  -> session waits for NPC safety point
  -> DynamicContentStore writes revision atomically
  -> GameState records active revision reference when needed
  -> future interactions execute the new Rust-compiled program
```

三条流程的共同点是先构造候选，再验证，再原子提交。任何失败都保留原状态和原修订。这个模式与当前 `Battle::submit`、`GameState::transition` 的候选状态做法一致，应成为跨系统的统一规则。

## 存档 envelope 的演进

当前 `SaveEnvelope` 已有格式版本、内容版本、checksum 和 `GameState`，并在读写时验证状态。未来应该保留这一方向，但它需要从单个 `content_version` 扩展为显式引用图。

```text
SaveEnvelope vNext
  format_version
  game_build_compatibility
  base_content_package_id + revision + hash
  battle_ruleset_id + revision
  data_snapshot_id
  dynamic_content_revision_refs
  player GameState
  active session checkpoint (optional)
  event/battle replay references or log segment
  checksum / integrity metadata
```

`dynamic_content_revision_refs` 不能只写“使用了模型”。它需要列出每个仍被游戏状态或 continuation 引用的动态 DSL 修订。若修订保存在本地内容仓，存档加载器先检查哈希；找不到时按产品策略处理：从打包快照恢复、使用兼容旧基线、执行明确迁移，或拒绝加载并给出可恢复诊断。绝不能在加载时悄悄要求模型重新生成“差不多的版本”。

## 存档与动态内容的四种策略

| 策略 | 做法 | 优点 | 风险 | 首发建议 |
| --- | --- | --- | --- | --- |
| 完整嵌入 | 将已激活 DSL/文本快照写进存档 | 自包含，模型无关 | 存档变大，内容重复 | 适合少量动态 NPC。 |
| 本地仓引用 | 存档写 revision/hash，内容仓保存产物 | 多个存档复用，便于审计 | 内容仓丢失会阻塞加载 | 需要备份与恢复策略。 |
| 包内提升 | 动态修订定期审核并并入内容包 | 易发行、易共享 | 个体差异需要迁移 | 适合作者批准的内容。 |
| 混合 | 关键修订嵌入，常规修订引用并可回填 | 平衡体积与可靠性 | 实现更复杂 | 长期目标。 |

第一版应选择一个简单策略，优先保证“单机存档拷走后仍能加载”。在模型本地生成的产品方向下，完整嵌入或带可回填快照的本地仓引用通常比只记 ID 更可靠。性能优化可以后做，数据丢失不能后补。

## 迁移

迁移要分别处理四类版本：存档格式、内容包、规则包和动态 DSL。把它们全塞进一个 `version: 2` 会让诊断无法行动。

| 变化 | 例子 | 允许的处理 |
| --- | --- | --- |
| 存档格式 | 字段拆分、新 checksum | 纯结构迁移；失败拒绝。 |
| 静态内容 | 地图坐标调整、NPC ID 重命名 | 显式 ID 映射或内容版本锁定。 |
| 规则包 | 伤害/招式/机制改变 | 旧存档锁旧规则，或只在安全点迁移并重验队伍。 |
| 动态 DSL | 新指令、旧 continuation 不兼容 | 提供程序迁移、完成旧脚本、回退基线，或保留旧解释器。 |

每次迁移必须在克隆状态上运行并重新 `validate`，成功才替换原存档。迁移报告要说明改变了什么、未改变什么、是否有玩家可见影响。不能因为加载器“尽量容错”而删除未知 flag、把 NPC teleport 到出生点或恢复满血。

## 失败恢复

产品应按故障性质给出不同恢复路径。

| 故障 | 游戏状态 | 恢复策略 |
| --- | --- | --- |
| 模型生成失败 | 未改变 | 继续旧 DSL，记录候选失败。 |
| 候选编译/模拟失败 | 未改变 | 保留诊断，允许之后重试/人工编辑。 |
| 激活事务失败 | 未改变或回滚 | 不更新 revision 引用。 |
| 内容包加载失败 | 不启动该存档会话 | 显示缺失包/版本/哈希诊断，提供恢复副本。 |
| 存档 checksum 错 | 不信任该文件 | 拒绝加载，保留原文件与备份，不自动修复。 |
| 进行中战斗中断 | 从最近安全 checkpoint 恢复 | 重放已提交动作，或按明确策略返回战斗前。 |
| 原生 runtime 崩溃 | 核心状态未直接损坏 | 重启后加载最后完整存档/检查点。 |
| 规则包不兼容 | 不静默改变结果 | 选择旧规则运行、迁移或拒绝。 |

自动保存必须只发生在定义的安全点，或使用完整事务日志。不要在每帧把半完成 UI/事件状态序列化并希望加载器猜测如何恢复。对于动态 DSL，安全点也决定何时可以引用新修订。

## 审计与 provenance

需要审计的不是模型“思维过程”，而是影响内容和玩家状态的可复现事实。动态 DSL 至少记录：

- 模型/模板/DSL schema 版本；
- 输入事实 schema 与脱敏摘要哈希；
- 基线 NPC/内容/规则包版本；
- 候选源、编译产物和文本资产哈希；
- 静态分析、模拟与内容政策诊断；
- 激活策略、逻辑时间、审阅者或自动规则；
- 当前修订、前一修订与回退指针；
- 该修订影响的存档或内容包范围。

审计记录不能包含不必要的完整玩家数据、模型密钥、原始隐私文本或外部服务响应。真正需要重放的是 DSL 编译产物、内容版本和游戏输入，不是模型服务器的内部状态。

## 内容质量与端到端验证

目前的 crate 单测很重要，但正式内容还需按场景验收。每个内容包应提供至少一条完整 scenario：

```text
加载内容包与规则包
  -> 新游戏
  -> 走到 NPC 并激活基线 DSL
  -> 在安全点激活动态 DSL 修订
  -> 与 NPC 交互并执行预制对白/事件
  -> 进入真实训练师或野生战斗
  -> 回写结果并保存
  -> 重启后加载同一动态修订
  -> 验证位置、队伍、flag、NPC continuation 与回放一致
```

场景应在无窗口的 application 层先跑通，再由 `game-host` 做实际输入、渲染和平台验收。窗口截图只能证明表现，不证明存档、战斗和动态内容版本的业务一致性。

质量层级建议如下：

| 层 | 主要断言 | 典型工具位置 |
| --- | --- | --- |
| Domain/foundation | ID、规则、数据、状态不变量 | 对应 crate 单测。 |
| Application | 命令到事件/状态、动态 DSL 激活、存档迁移 | 产品会话与内容测试。 |
| Content | 引用、可达、规则合法、DSL 编译和模拟 | 内容 CLI/编辑器后端。 |
| Adapter | 文件/模型/存储错误转换、限额、哈希 | adapter 测试替身。 |
| Runtime | 启动、输入、真实加载、GPU/窗口边界 | `ops run` 与平台 smoke。 |
| E2E | 完整垂直切片和回归存档 | `game-e2e` 或新增质量套件。 |

所有公共验证入口继续通过 `ops` 暴露。新的内容检查、动态 DSL 验证、回放比较和存档迁移测试应成为明确 suite，而不是藏在开发者私有脚本中。

## 发布流程

发布内容与发布二进制需要可分离，但兼容关系要明确。一个安全流程如下：

1. 作者/模型生成候选内容，进入临时仓。
2. Rust 编译器、分析器、模拟器与资源检查器生成报告。
3. 审阅者批准静态内容和要进入发行的动态 DSL 修订。
4. 打包器构造 manifest、哈希、规则包与数据引用。
5. CI/`ops` 运行内容、规则、存档迁移和垂直切片测试。
6. 发行者将内容包标记为可用，并保留前一版本和迁移说明。
7. runtime 按兼容策略加载；存档第一次使用新包前可创建备份。
8. 发现回归时，回滚到前一包或禁用特定动态修订，不改写玩家历史。

动态 DSL 的本地自动激活与正式发行不冲突。前者可只影响单个本地档案，并以安全规则自动批准；后者影响所有用户，仍要经过人工内容审阅与完整回归。两个层级不能共用一个“发布”按钮。

## 阶段计划

### P0：事实基线与兼容清单

记录当前 `game-session`、`game-foundation`、地图、叙事和 battle crate 的状态所有权与测试范围。列出两个会话模型重叠字段、现有存档格式、内容来源和未实现接口。退出条件是任何人都能解释“当前哪个路径真实运行，哪个路径只用于薄切片”。

### P1：产品会话和真实战斗桥接

先把真实 `BattleSession` 的开始、生命周期、结束结果与 `GameState` 接通。不要先扩展物种数或模型功能。退出条件是一条世界遭遇和一条训练师对战都使用实际规则，且 HP/PP/异常/奖励/训练师状态原子回写。

### P2：内容包 MVP

把现有地图、NPC、训练师和文本从 demo/常量路径导入 manifest 驱动的内容包。退出条件是同一产品会话能加载一个版本化区域，校验引用，且编辑器/CLI/host 读取同一份内容定义。

### P3：事件运行时与基线 DSL

实现最小事件程序、交互解析和预制文本资产，使静态 NPC 全部由 Rust DSL 执行。退出条件是起始区域从领取到战后续体完全由内容包 DSL 驱动，并可保存/加载。

### P4：动态 DSL 仓与本地模型生成

增加候选仓、编译/分析/模拟、闲时调度与安全激活。先选一类低风险 NPC，例如路线引导或战后闲聊的后续行为。退出条件是本地模型生成失败不影响游戏，成功修订在存档后无需模型即可重放。

### P5：规则包与 AI 对战同步

将对战规则包、训练师 AI profile、回放和内容包 manifest 统一版本。退出条件是模型 AI 对战与动态 NPC DSL 都能在同一规则/内容版本下被审计、关闭或回退。

### P6：长期试玩与发布

扩大区域和动态 NPC 覆盖，执行旧存档迁移、内容回滚、崩溃恢复、性能、离线和权利检查。退出条件是至少一个完整区域在真实 host 中稳定试玩，且所有动态变化可追溯和恢复。

## 风险

### 把模型产生的 DSL 当作“临时数据”不保存

这会使玩家第二天无法加载存档，或加载后角色行为与昨日不同。解决：动态 DSL 一旦激活就成为版本化内容事实，保存其 ID/哈希并按策略嵌入或备份产物。

### 静态与动态 NPC 各自拥有 flag

这会出现“静态脚本认为礼物没领，动态脚本认为已领”的双重事实。解决：所有长期 flag/变量由统一 `GameState` 定义；DSL 只通过事件运行时读写，模型不拥有另一份记忆库。

### 让生成器在战斗/事件中途热更新

这会破坏 continuation、回放和奖励原子性。解决：只在安全点激活；旧脚本完成或有明确迁移后才换版本。

### 把内容包升级与规则升级混为一谈

地图修复不应默默改变伤害公式，规则升级也不应被当作普通资源更新。解决：manifest 分别引用内容、数据和规则包；迁移/回滚各自处理。

### 把审计做成海量原始模型日志

这会带来隐私、体积和检索负担，仍无法保证可重放。解决：保存结构化来源、哈希、编译产物和验证结果；按需在受控环境保留短期调试记录。

## 完成标准

内容运行时、存档与交付的 MVP 完成时，应同时满足：

1. 真实世界、事件、战斗和长期玩家状态由一个产品会话协调，不存在需要手工同步的第二份真相。
2. 静态 Rust 内容、规则包、数据快照、地图、NPC、训练师和资源都由版本化 manifest 引用并校验。
3. 动态 NPC 由本地模型在闲时/触发窗口生成 DSL 候选；Rust 编译、分析、模拟、在安全点激活，并在运行时独占执行权。
4. 激活的动态 DSL 有稳定修订、基线、哈希、来源和回退；模型离线时旧存档与旧 NPC 行为仍可运行。
5. 存档能验证并恢复内容/规则/动态 DSL 引用；不兼容、损坏或缺失内容给出明确恢复路径而非静默改变状态。
6. 一条端到端场景证明新游戏、NPC、动态 DSL、真实战斗、战后回写、保存、重启与加载一致。
7. 所有内容、迁移、回放和原生验收通过项目 `ops` 入口执行，结果可归因。

达到这些条件，项目才能同时拥有稳定的 Rust 静态基础和真正可持续演进的模型驱动动态 NPC，而不是在两者之间留下难以恢复的状态裂缝。
