# AI 地图生成

> 分类：未来；起草：2026-07-21。
> 状态：开发期内容创作提案。AI 生成的地图默认是候选草案，不是可直接发布的游戏内容。

## 结论

AI 地图生成的正确产品形态是“受约束的地图候选工作台”：作者给出区域意图与约束，模型输出一个版本化结构化候选，系统把候选导入临时项目并运行结构、语义、可达性、资源和玩法模拟检查，作者在编辑器中审阅和修改，批准后才生成正式内容包变更。

不应让模型直接输出像素图、直接写 `maps/`、直接调用发布命令，或在运行时随机生成正式路线。当前地图已经有项目模型、编辑器、JSON/G3MP 存储、瓦片语义和可投影世界的基础。未来工作要把这些现有边界变成 AI 可用的候选合同，而不是另起一套不可编辑的生成格式。

## 当前依据

当前 workspace 已提供以下可复用能力：

- `map-project` 定义带版本的地图项目、视觉 cell、碰撞 cell、遭遇事件和编辑历史；`FORMAT_VERSION` 已明确为 `gen3-map-v2`。
- 地图编辑器、CLI 和存储 adapter 已能读写、校验和打包现有地图项目。
- `world-domain` 用 `TileMap` 处理网格、可走性、阻挡和草丛遭遇；`world-project` 已能处理多个地图分区与边界/空区的投影。
- `world-application` 能从地图项目构建可观察的世界角色，并把 actor 的位置、朝向、外观与最小脚本绑定在一起。
- `maps/verdant-route/` 已展示十张相邻地图及 `world.json` 的现实内容布局。它是人工作品，不应被误称为 AI 生成样例。

当前模型仍有局限：地图事件主要是 `Encounter`；地图内容与未来 `game-foundation` 的静态 `MapDefinition`、NPC/事件定义尚未形成统一正式内容包；跨图玩法验证、任务可达性、奖励经济和训练师分布都还没有可发布的全局契约。因此 AI 地图必须以“候选”身份进入，直到内容运行时在 [006 内容运行时、存档与交付](006-内容运行时存档与交付.md) 中收敛。

## 为什么地图生成不能从图像开始

图像模型可以很快生成一张看起来像像素地图的图片，但图片不知道格子碰撞、warp、出生点、草丛、物件 ID、资源授权、邻接边缘或任务可达性。把图片再反向描图会把最重要的规则交给人工猜测，生成效果越好，错误越难发现。

正式地图的最小事实是结构，而不是画面：地图 ID、尺寸、分层 tile、碰撞、逻辑区域、连接、出生点、对象、触发器、遭遇表、资源引用和版本。美术表现可以从结构投影，也可以由人类或 AI 辅助提出，但不能替代结构。生成流程应该先生成拓扑与玩法约束，再生成 tile 布局和装饰，最后才处理视觉变体。

## 三层地图模型

未来内容系统应明确区分三个层次。

| 层 | 包含内容 | 谁可以修改 | 验证重点 |
| --- | --- | --- | --- |
| 玩法拓扑层 | 区域、地图节点、连接、warp、目标、锁/钥匙、可达性约束 | 作者、AI 候选、审阅者 | 是否可从出生点到目标；是否存在软锁。 |
| 逻辑网格层 | 尺寸、地形、碰撞、遭遇区、对象位置、触发区域 | 编辑器、AI 候选 | 碰撞、边缘一致性、对象重叠、区域引用。 |
| 表现层 | 瓦片、装饰、光照标签、外观、音景与资源引用 | 美术/地图作者、AI 候选 | 资源存在、图层规则、可读性、风格一致性。 |

当前 `MapProject` 已覆盖部分逻辑网格和表现层。未来不必马上大改它，但新内容包需要能把每层关系表达清楚。若一条道路“看起来连通”而碰撞层阻塞，校验器要报告逻辑错误；若逻辑连通但缺少瓦片，渲染/资产校验要报告表现错误。不要用一种 cell 值同时承载所有未来语义。

## 候选生成合同

模型不能直接产出任意 JSON。它应填充一个小而稳定的候选 schema。第一版不需要覆盖所有地图功能，只需要支持首区域的必要结构。概念上：

```text
MapGenerationRequest
  project context
    - content package version
    - tileset/material catalog summary
    - ruleset and allowed encounter table IDs
    - neighboring map edge contracts
  author intent
    - biome, mood, narrative role
    - start/end anchors
    - required POIs and NPC slots
    - pacing and difficulty budget
  hard constraints
    - dimensions/ranges
    - traversal requirements
    - forbidden resources/features
    - no-new-ID policy or allowed ID namespace
  generation profile
    - template version
    - seed / determinism request
    - variation count

MapCandidate
  manifest
    - candidate ID, schema version, source summary, provenance
  topology proposal
  grid diff or full grid
  objects and triggers
  encounter-zone references
  resource references
  rationale labels (optional, non-executable)
```

请求中的“项目上下文”必须是压缩后的正式摘要，而不是整个仓库、全部资产路径或其他地图的原始文件。这样既节省成本，也防止模型接触不必要的数据。候选中的 rationale 只帮助作者审阅，不能被 loader 当作规则。

## 约束优先的生成顺序

每次生成应按以下顺序展开。模型可以一次返回完整候选，但校验器和 UI 要把错误归到具体阶段。

### 1. 区域意图与玩法骨架

作者先给出“这张图在游戏循环中做什么”。例如，它是起始镇的出口、教学路线、可选支路、资源补给点、训练师密集区域或剧情转折前的安静区域。必须同时给出入口、出口、目标、最少/最多训练师、遭遇区比例、可选物和禁止元素。

AI 可提出多个拓扑方案，但每个方案都以节点和约束表达，而不是画成无语义图片。此时验证目标是连通与节奏，不是美术。

### 2. 连接合同

每个跨图连接有稳定 ID、来源边界/触发点、目标地图/位置、朝向或入口语义、双向或单向属性，以及对相邻边缘的几何契约。当前 verdant-route 的公共边缘逐格对齐是有价值的现成实践；未来生成器必须读取邻接地图的边缘合同，不能随意覆盖。

如果地图尚未存在，候选应声明“需要新建邻接地图”而不是制造通向空白的出口。发布校验要拒绝目标不存在、连接不对称、出口被碰撞封死、warp 目标不可走或会把玩家带到对象重叠位置的候选。

### 3. 可走网格与逻辑区

把拓扑投影为可走格、阻挡格、草丛/遭遇格、道路、地标和对象预留位。生成器应先满足硬约束：出生点可走、目标可达、入口连通、NPC 不封死路径、遭遇区可进入、重要物件可接近。装饰不应在此阶段破坏路网。

可走网格要被图算法验证，而不是只由模型自评。对于每个关键锚点执行 flood fill 或等价搜索；对于可选区域计算是否有绕路；对于单向机关模拟返回路径；对于训练师/阻挡 NPC 计算其激活前后可达性。若项目将来有推箱、开关或动态桥梁，验证器必须在状态图上搜索，而不是只看静态 tile。

### 4. 对象、触发器与玩法预算

NPC、物品、训练师、商店、恢复点、脚本触发器和遭遇表是内容实体，不是 tile 文本。候选只引用已有稳定 ID，或在受控 namespace 中创建待审实体。任何新实体都要通过对应的 NPC、训练师或事件校验器。

玩法预算应由内容作者给定，例如首路线最多两名训练师、总经验目标区间、可获得伤药数量、草丛覆盖范围和等级带。AI 可以在预算内分布，不能擅自提高奖励或引入规则包未支持的物种/招式。地图生成器不是经济平衡的权威。

### 5. 表现与装饰

最后才生成材料选择、草丛簇、道路形状、树冠、地标、留白和视觉节奏。表现在不改变逻辑层时可有较大自由；若某个装饰需要阻挡、遮挡或特殊交互，就要回到逻辑层并重新验证。编辑器应让作者分别查看碰撞、遭遇、对象和表现层，避免“漂亮但不能走”的误判。

## 校验管线

候选进入临时工作区后，应依次通过以下门槛。任何门槛失败都保留候选和诊断，不写正式内容包。

| 门槛 | 输入 | 检查 | 典型失败 |
| --- | --- | --- | --- |
| Schema | 候选 JSON/二进制 | 版本、字段类型、尺寸上限、ID 格式 | 缺少地图 ID、数组过长。 |
| 资源 | tile/material/appearance 引用 | 目录中存在、许可状态、可加载 | 生成了不存在的瓦片名。 |
| 结构 | 地图项目与连接图 | 边界、尺寸、入口、重复 ID、对象重叠 | warp 指向不存在地图。 |
| 逻辑 | 碰撞、出生点、对象 | 可走性、阻挡、角色占据 | 玩家出生在树上。 |
| 可达性 | 状态图与目标 | 起点到目标、返回、软锁、关键点 | 训练师封住唯一出口。 |
| 内容 | 遭遇/训练师/NPC 引用 | 规则包、等级、奖励和事件兼容 | 未支持的招式进入训练师队伍。 |
| 表现 | 图层与视图投影 | 资源加载、遮挡、可读性、无越界 | 视觉 cell 与碰撞层错位。 |
| 模拟 | 小型玩家/脚本动作序列 | 进入、交互、遭遇、离开、保存 | 事件执行后无法返回。 |
| 人工审阅 | 可视化 diff 与报告 | 节奏、风格、叙事与质量 | 逻辑可过但不符合区域主题。 |

验证器的输出应是一组结构化诊断，而不是一段大语言模型解释。诊断至少包含 code、严重度、地图/对象 ID、坐标或路径、原因、可能修复方式和关联候选版本。模型可以在作者点击“尝试修复”后读取这些诊断再生成新候选，但它仍然不能直接批准自身修复。

## 生成与编辑的关系

AI 不应成为第二个编辑器。正确关系是：

```text
自然语言意图 / 结构化约束
  -> AI 生成候选
  -> 临时地图项目 + 校验报告
  -> 地图编辑器显示分层 diff
  -> 作者手工编辑、接受或部分接受
  -> 再校验
  -> 审阅批准
  -> 内容包提交
```

编辑器至少要提供：候选与基线的差异视图；碰撞/遭遇/对象/资源层切换；错误坐标定位；可达性路径可视化；候选版本历史；来源与提示模板摘要；按区域或对象的接受/拒绝操作；导出审阅报告。它不应把“重新生成”设计成覆盖当前已批准地图的一键操作。

用户可手工修改 AI 候选。修改后 provenance 应记录“候选经人工编辑”，而不是继续宣称整张图由模型原样生成。内容质量归属应以最终审阅者为准。

## 生成器类型

不同地图任务适合不同生成方法。不要把语言模型当成所有几何问题的最佳工具。

| 生成器 | 最适合的层 | 适合做什么 | 不适合做什么 |
| --- | --- | --- | --- |
| 规则/模板生成 | 网格与边缘 | 道路、边框、房间、连续区域、固定约束 | 新颖叙事和风格方案。 |
| 图搜索/约束求解 | 拓扑与可达性 | 满足入口、目标、锁钥、预算 | 自然语言主题理解。 |
| 语言模型 | 意图转结构、命名、候选布局、审阅建议 | 把“雾林支路、有两条回路”变成候选 | 精确碰撞和数学验证。 |
| 图像/风格模型 | mood board、装饰参考 | 视觉探索与人工参考 | 正式 tile/碰撞源。 |
| 人类编辑 | 最终玩法、例外与审美 | 取舍、叙事节奏、发布责任 | 大量重复布局。 |

推荐采用混合生成。语言模型先提出拓扑与语义标签；约束求解器在硬条件下构造网格；规则模板填充安全的边缘和道路；模型在有限位置提出装饰；人类在编辑器中完成最终取舍。这样失败更容易定位：是意图有歧义、求解不可满足、资源缺失还是审美不合格。

## 种子与可重现性

候选生成需要区分“模型非确定”与“内容不可重现”。即便模型服务不能保证逐 token 一致，系统仍应记录：候选输入摘要、模板版本、模型/参数标识、生成时间、随机 seed（若适用）、原始结构化输出哈希、校验版本和作者决定。最终发布的是候选的规范化内容产物及其哈希，而不是要求日后重新调用模型得到同一结果。

对于规则/模板生成部分，必须使用明确 seed 并可本地重放。这样一个可达性 bug 可以在不调用模型的情况下重现。对于语言模型部分，保存输入/输出的合规摘要和完整候选文件即可；重新生成只用于探索，不用于证明旧版本。

## 地图生成的安全边界

模型输入和输出都是不可信数据。安全要求包括：

- 限制候选文件大小、地图尺寸、对象数、文本长度、递归深度和资源引用数。
- 所有路径使用逻辑资源 ID，不接受模型提供的绝对路径、`..`、URL 或 shell 片段。
- 不自动下载资产、不执行模型返回的脚本、不使用模型输出拼接命令行。
- 在隔离临时目录/内存项目验证，只有审批服务可以将规范化产物写入内容包。
- 对每次生成设置预算、取消和速率限制；避免批量请求意外消耗费用或生成海量文件。
- 对人物、地点、商标和外部文本做内容政策与来源审阅；不要让模型把不明来源素材直接混入发行资产。

这些限制不妨碍创作。它们让生成失败变成可管理的候选，而不是仓库污染或安全事故。

## 地图质量度量

地图质量不等于校验通过。校验只说明没有已知结构错误。建议分层统计：

| 指标 | 说明 | 用途 |
| --- | --- | --- |
| 结构通过率 | 候选通过 schema、资源、连接和逻辑检查的比例 | 发现 schema/提示质量问题。 |
| 可达通过率 | 所有必经目标可达且无检测到软锁的比例 | 防止漂亮空壳。 |
| 人工采纳率 | 被接受的候选/局部 diff 比例 | 判断生成是否真正节省创作时间。 |
| 修改密度 | 作者接受后仍修改的格子/对象比例 | 区分可用骨架与低质量装饰。 |
| 试玩缺陷率 | 已发布地图中的卡死、不可读、节奏问题 | 证明模拟覆盖盲点。 |
| 重复度 | tile/道路/布局模式的多样性与过度重复 | 防止模型模板痕迹。 |
| 内容预算偏差 | 实际经验、物品、训练师密度对设计目标的偏差 | 保护难度曲线。 |

指标应帮助作者改进模板和约束，而不是变成“自动批准分数”。高采纳率可能来自作者只让模型做简单任务；低采纳率也可能来自探索性概念期。最终决定仍需要审阅者。

## 实现阶段

### M1：把现有地图能力固化为机器可读诊断

先不接模型。补齐或整理地图项目、世界投影、存储和 CLI 的结构化错误与可达性检查。以 verdant-route 和 demo map 建立 fixture。退出条件是对坏地图能精确报告坐标和规则，对好地图能生成稳定报告。

### M2：候选 schema 与临时导入

定义最小 `MapCandidate`，只覆盖单张地图、既有材料、固定尺寸、碰撞、遭遇和对象预留位。实现“导入临时项目 -> 校验 -> 展示 diff”，暂不允许新资源或跨图连接。退出条件是手写候选能完整走过该流程且不触碰正式文件。

### M3：规则/模板生成器

先写不依赖模型的道路、边缘、草丛和可达性模板生成器，接受相同候选 schema。退出条件是给定 seed 可重现，并能通过所有校验。它将成为 AI 输出的修复和回退工具。

### M4：模型提出拓扑与约束

接入模型生成有限的拓扑/布局草案，所有网格仍由求解器或模板填充。退出条件是模型输出无效时得到结构化诊断，作者能以诊断驱动重新生成，且未批准内容不写入项目。

### M5：多图区域与内容关联

扩展到连接图、NPC/训练师槽位、遭遇表和玩法预算。退出条件是候选区域能从出生点到目标完成一次真实游戏垂直切片，并通过模拟与人工试玩。

### M6：编辑器工作台与发布审阅

增加 provenance、差异接受、评论、审批、导出和内容包签名/manifest 集成。退出条件是任何已发布地图都可追溯到审核记录，并能回滚到前一内容包。

## 常见失败与处理

### 看起来连通，实际上不可走

原因通常是表现层道路与碰撞层脱节，或对象覆盖了唯一入口。处理：优先显示碰撞路径和 actor 占据层；把路径搜索作为发布门槛；不要让截图审阅代替逻辑检查。

### 生成地图重复且没有节奏

原因通常是提示只写了生物群系，没有写玩法角色、入口/出口、可选支路、训练师预算和地标。处理：丰富请求的结构化意图，让模型只补充创意而非猜约束；统计重复度并为模板引入多种安全变体。

### 模型编造资产或规则

原因是输入给了自然语言列表而没有给受限 ID 枚举。处理：向模型提供短 ID/显示名表，输出只允许引用枚举；校验器拒绝未知引用；UI 提供最近合法项供作者替换。

### 修复一处导致另一处坏掉

原因是模型得到一段错误文本后重写整张图。处理：支持局部 diff、锁定已批准区域、限制可修改边界，并在每次 patch 后重跑全局连接和可达性验证。

### 生成任务泄露内容或成本过高

原因是把整个项目、完整叙事或资产目录作为上下文发送。处理：提供最小内容摘要、按区域切片、保存候选缓存、设置预算与删除策略，并允许完全离线的模板路径。

## 完成标准

AI 地图生成 MVP 完成时，至少达到：

1. 生成内容使用现有或明确演进后的地图项目/内容包 schema，而不是私有图片格式。
2. AI 输出只能进入临时候选区；未经过结构、逻辑、可达性、资源和人工审阅不能发布。
3. 生成器、校验器和编辑器可以精确定位失败地图、坐标、对象或连接。
4. 已批准候选能在正式世界运行时加载、从出生点完成目标流程，并可保存/重载。
5. 每个候选和正式地图有版本、来源、校验报告、审阅结果和可回滚的 manifest。
6. 模型服务关闭时，作者仍可使用编辑器和确定性模板创建、修改、验证和发布地图。

这样，AI 生成地图才会成为内容团队可依赖的工具，而不是一次性视觉演示。
