# 宝可梦游戏未来发展总纲

> 分类：未来；起草：2026-07-21。
> 状态：长期产品与技术提案。本文不表示任何功能已经完成，也不构成排期承诺。

## 一句话目标

把当前 Rust workspace 发展成一款可离线游玩的单人宝可梦式 RPG：使用前 386 种宝可梦作为内容边界，使用一个明确冻结、可回放验证的现代对战规则包作为对战边界；玩家可与确定性 AI 或受限模型 AI 对战；创作者可让 AI 提交候选地图和候选 NPC，再由本地校验、人工审阅和版本化内容包决定是否进入游戏。

这里的重点不是“让模型直接生成游戏”。重点是建立一条可验证的生产线。任何一次模型输出都只能成为候选内容或受限命令。规则、存档、发布版本和玩家状态仍由本地确定性系统拥有。

## 当前起点

当前 workspace 并非从空白开始。以下结论来自当前代码，且只描述已经可读到的边界：

- `battle-domain` 已实现第三世代风格的双人确定性回合状态机。它持有队伍、命令、种子、事件历史和天气。调用方以合法动作查询和原子提交驱动它。
- `battle-application` 为双方分别提供受视角限制的观察，并能从 checkpoint 取得增量事件和前后快照。`battle-session` 负责玩家动作、对手策略、回放队列和强制换人的交互阶段。
- `game-data` 已嵌入经校验的第 1 至 386 号图鉴数据；数据集包含宝可梦、招式、属性、能力和学习表等只读记录。该事实不等于当前对战已经实现全部这些规则。
- `world-domain` 已把网格、移动、阻挡、草丛遭遇和 NPC 占位放进纯状态转换。`world-application` 已能把地图项目投影为世界，并按逻辑 tick 推进 actor 绑定的最小叙事脚本。
- `game-foundation` 已完成一条纯状态的验证切片：新游戏、赠送 NPC、warp、草丛遭遇、战斗结果回写、训练师一次性挑战、商店购买、存档重载。它仍用 `ResolveBattle` 接收摘要结果，而不是实际 `BattleSession` 的完整状态。
- `game-ramus-adapter` 已证明可以把玩家和 AI 的同一份受权 DSL 调用路由为类型化游戏命令或存档意图；它不保存 `GameState`，也不读写文件。
- `game-host` 已是原生游戏的装配点。现有 `GameSession` 仍以 demo roster 和当前世界场景驱动实际运行路径，因此它与 `game-foundation` 尚未合并为一个产品会话。

这几个事实决定了发展顺序。先消除两套游戏会话和两套战斗结果语义之间的断裂，再扩大规则和内容；先让 AI 使用现有的“观察 -> 受限动作 -> reducer”方向，再讨论自主 agent、联网或生成式玩法。

## 终态产品边界

终态产品由六个相互制约的子系统组成。

```text
离线内容包 + 玩家存档
        -> 游戏应用状态与事件运行时
        -> 世界、交互、遭遇、训练师、战斗编排
        -> 确定性规则核心
        -> 快照、事件、回放与表现

AI 对战：只读观察 -> 受限动作 -> 同一规则核心
AI 地图：结构化候选 -> 校验/模拟 -> 人工审批 -> 内容包
AI NPC：结构化候选 -> 编译/静态分析 -> 语义测试 -> 内容包
```

玩家体验应当是传统单人探索与回合制对战，而不是聊天窗口驱动的沙盒。静态内容与确定性执行归 Rust；需要随世界、玩家进度或创作目标变化的 NPC 内容归本地模型，但模型只产出 DSL 候选，不能直接执行或写入状态。静态与动态 NPC 必须共用同一套 DSL、编译器、中间表示、执行器、存档 continuation 和测试工具；差异只由内容来源与 capability profile 表达，不能为模型另建一门执行语言。模型能力服务于三类功能：

1. 对战对手。模型或本地算法根据它能看见的战场信息选择一个合法动作。它不读取隐藏队伍、随机数、未来事件或内存地址。
2. 创作辅助。模型生成地图、NPC、对白、训练师队伍和事件草案。草案必须可导入编辑器、可追溯、可回退，并且默认不发布。
3. 动态 NPC 内容。模型在闲时或由受控触发器唤起，基于已公开的游戏事实生成下一段 NPC DSL、预制对白或行为变体。Rust 编译、校验、模拟并冻结通过的产物；未通过前，NPC 继续执行上一版 DSL。模型不能即席修改地图、奖励、数值、剧情 flag 或战斗结果。

“前 386 种宝可梦”是内容选择，不自动决定规则时代。对战规则需要显式选择一个规则包版本，例如“以某一现代世代的单打基础规则为目标，删除超出内容边界的物种、招式、机制与道具”，并将这个选择编码为版本化数据。未经选择，任何“最新世代”说法都只是方向，不是可实现的规范。

## 非目标与硬约束

以下边界在整个路线中保持有效，除非单独通过新的提案改变：

- 不把任何模型服务、HTTP 客户端、提示词、令牌、云凭据或真实时间引入 `foundation`、`domain` 或确定性 application reducer。
- 不让模型直接写存档、地图正式文件、资产目录、Rust 源码或 Git 工作区。模型只能输出受限文本或结构化候选，由 adapter 和审批入口处理。
- 不让 UI、runtime 或 AI adapter 直接改写 `GameState`、`Battle` 或 `World` 的内部状态。它们只能提交类型化命令。
- 不以“模型通常会做对”为验收。每一类模型输出都要有结构校验、语义校验、失败诊断、回滚路径和离线替代路径。
- 不把宝可梦名称、形象、游戏数据或其他受权利约束内容当作可自由再分发资产。数据来源、许可、商标使用和最终发行范围必须单列法律审查；本路线不提供法律结论。
- 不在完成可重放的单人闭环前承诺联机对战、实时多人世界、用户生成内容广场、云端持久世界或开放式 agent。
- 不以直接调用 `cargo` 或手工 Windows 命令作为项目公共流程。项目公开开发与验收入口继续由 `ops` 提供。

## 四条主线

### 主线 A：可玩的确定性核心

目标是把“可保存的世界状态”和“可回放的真实战斗”接成一个会话。它优先于地图数量、UI 美化和模型接入。若一场对战结束后无法明确回写 HP、PP、异常、经验、金钱、训练师状态和事件 flag，那么模型再聪明也无法形成完整游戏。

### 主线 B：版本化规则与数据

目标是让“现代对战、前 386 种内容”成为可审计配置，而不是散落在 match 分支里的猜测。规则包、数据快照、机制开关、平衡修正、测试样本和存档兼容策略共同构成一个可冻结的发行合同。

### 主线 C：AI 作为受限参与者

目标是让 AI 与人类玩家、规则型 AI 共用观察和动作边界。模型失败、超时、格式错误、越权调用和质量下降都必须能回退到确定性策略，不应中断游戏或污染状态。

### 主线 D：AI 作为受控创作工具

目标是让 AI 把自然语言意图变为可编辑的候选内容，而不是替代内容系统。地图生成从拓扑和规则开始，NPC 生成从角色合同、事件效果和文本资产开始。最终进入产品的是通过校验和审阅的内容包，不是原始对话。

## 阶段顺序

阶段按依赖关系排列，不按日期承诺。一个阶段未达到退出条件时，不以并行开发为理由跳过它。

| 阶段 | 核心交付 | 为什么在此时做 | 退出条件 |
| --- | --- | --- | --- |
| 0. 基线固化 | 当前 crate 图、测试状态、薄切片样本、内容来源清单 | 先区分已存在的能力与假设。 | 有可复现的基线报告和失败归因。 |
| 1. 产品会话收敛 | `game-foundation` 与实际世界/战斗编排的融合方案 | 先消除两条游戏状态路径。 | 一条真实会话能从世界进入实际战斗并回写结果。 |
| 2. 规则包 MVP | 前 386 内容过滤、规则版本、可执行能力矩阵 | 对战是 AI 与游戏循环共同的底座。 | 回归样例和可重复回放覆盖 MVP 规则。 |
| 3. AI 对战 MVP | 观察 DTO、动作 schema、预算、回退策略、对局基准 | 只在合法动作与回放已稳定后接模型。 | 模型、启发式和人工客户端可互换。 |
| 4. 内容包 MVP | 地图、NPC、训练师、事件、资源和版本 manifest | 让真实游戏内容摆脱 demo 常量。 | 内容包可校验、加载、迁移和回滚。 |
| 5. AI 地图与 NPC 工作台 | 候选 schema、静态分析、模拟、人工审核和导出 | AI 创作需要先有确定的落点。 | 候选内容可重复生成、审阅、拒绝或发布。 |
| 6. 试玩与发行准备 | 长流程 E2E、存档迁移、崩溃恢复、性能/可访问性、权利清单 | 只有产品循环稳定后才扩大体验面。 | 可持续试玩版本具备发行门槛。 |

## 里程碑切片

路线不使用“先做完引擎，再做游戏”的计划。每个阶段都扩展同一条可试玩切片：

```text
创建角色
  -> 在起始地图移动并与 NPC 交互
  -> 获得初始队伍和一个道具
  -> 穿过连接进入路线
  -> 触发遭遇并完成真实战斗
  -> 将结果回写到队伍、世界和事件状态
  -> 与训练师对战且不能重复领取奖励
  -> 保存、退出、加载并继续
  -> 用同一份观察合同由人类、启发式或模型选择对方动作
  -> 在编辑器审阅 AI 生成的下一张候选地图和 NPC
```

每次新增规则、内容或模型能力，都必须说明它如何穿过这条切片，以及失败时如何回到上一个有效状态。没有贯穿切片的“完成”只算局部实验。

## 决策机制

本路线把决策分为三层。

| 决策层 | 例子 | 记录位置 | 可以由谁改变 |
| --- | --- | --- | --- |
| 产品宪法 | 前 386 内容边界、离线优先、AI 不直写状态 | 本目录总纲与专题 | 项目负责人明确批准。 |
| 发行规则包 | 对战版本、机制开关、平衡表、内容 manifest | 未来实现中的版本化数据和设计记录 | 规则维护者审批并通过回归。 |
| 内容实例 | 一张地图、一个 NPC、一段对白、一个训练师队伍 | 内容包与编辑器历史 | 内容审阅者在工具中批准。 |

模型不得替代任何一层审批。模型可以建议，不能授权。尤其是“模型给出一个看似合理的改动”不能被视为规则包、数值设计或剧情方向已经决定。

## 质量门槛

从第一天起，所有未来能力都应满足以下共同门槛。

1. 确定性：对给定内容版本、初始状态、命令序列与随机输入，核心产生相同的状态和事件。
2. 可观测：每个重要转换都有类型化事件、错误或诊断；不靠日志文本作为唯一事实。
3. 可回放：战斗和关键世界事件能从初始快照、输入和事件重建到一致结果。
4. 可隔离：模型、网络、文件、窗口和真实时间故障不污染核心状态。
5. 可迁移：存档和内容都有版本标识、兼容检查和明确的拒绝或迁移行为。
6. 可审阅：AI 生成内容保留来源、提示模板版本、输入摘要、模型标识、校验报告和人工决定。
7. 可替换：模型服务不可用时，游戏仍可用确定性策略、预制内容和本地编辑器运行。

## 度量而非口号

每条主线需要量化指标，但指标不能替代可玩性。

| 领域 | 初始指标 | 失效信号 |
| --- | --- | --- |
| 对战 | 规则案例通过率、回放一致率、非法动作不变性 | 相同种子出现不同结果；修复靠改测试期望。 |
| AI 对战 | 合法动作率、超时率、回退率、同信息对局胜率分布 | 模型经常请求不存在的动作，或胜率来自偷看信息。 |
| 地图 | 结构校验通过率、可达率、死端/软锁数、人工采纳率 | 生成了漂亮图却无法从出生点到目标。 |
| NPC | 编译通过率、事件可达率、重复奖励率、文本审阅退回率 | 对白可读但状态条件互相矛盾。 |
| 存档 | 加载成功率、迁移成功率、损坏拒绝率、重载一致率 | 新版本静默改变玩家进度。 |
| 试玩 | 完成切片时长、卡死率、崩溃恢复率、可复现缺陷比例 | 只能在开发机上手工重现问题。 |

## 近期优先级

下一次实现迭代不应从“接一个大模型 API”开始。推荐的最小顺序是：

1. 写出 `game-foundation` 与 `battle-session` 的集成设计和状态映射，不立即删除任一现有路径。
2. 选定一个可公开取得、可版本冻结的对战规则资料来源，并写出前 386 内容筛选和差异表。
3. 为真实战斗建立可序列化输入、初始状态、随机流与结果补丁合同。
4. 用一个不依赖网络的启发式 `OpponentPolicy` 通过新的 AI 观察/动作合同，作为模型 adapter 的金标准。
5. 将一张现有地图和一组预制 NPC 导入未来内容包 schema，证明内容不是只能通过 Rust 常量创建。

完成这些工作后，模型接入才有稳定的边界。此时模型只需完成“阅读观察，返回一个合法动作”或“返回一个候选内容文档”，而不必也不应理解整个 Rust 工作区。

## 暂不决定的事项

以下问题重要，但不能被本总纲暗中决定：

- 对战规则具体以哪个官方作品、哪个日期或哪个竞争格式为准。
- 是否包含太晶化等现代机制，以及它们如何与前 386 种内容相容。
- 发行平台、商业模式、联网功能、账号系统和云同步。
- 是否允许玩家在正式版内使用生成式工具，还是只面向开发者和编辑者。
- 美术风格、音乐来源、地区主题、剧情、角色名称和最终世界规模。
- 模型供应商、部署位置、费用上限、隐私策略和离线模型支持范围。

每项都需要单独的、可审阅的决策记录。没有决定之前，实现应保留扩展点，但不模拟一个并不存在的结论。

## 文档维护

未来文档随着决策收敛而缩短，而不是持续堆积历史。某项提案实现且验收后，应把能由代码和测试证明的部分移入相应的 `docs/v2/current/` 或 crate 文档；过期草案直接删除，通过 Git 历史追溯。实现中的临时进度、会议记录和模型对话不应塞进本目录。
