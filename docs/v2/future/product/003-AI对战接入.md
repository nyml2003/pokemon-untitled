# AI 对战接入

> 分类：未来；起草：2026-07-21。
> 状态：AI adapter 与产品策略提案。本文不承诺使用任何特定模型、云服务或供应商。

## 结论

AI 对战应该是一个可替换的“动作选择端口”，不是一条绕过对战规则的聊天链路。无论对手由手写启发式、搜索算法、本地模型还是远程模型驱动，它都只能接收一份按视角过滤的观察和一个有限的合法动作集合，并返回其中一个动作或明确放弃。`BattleApplication` 和 `BattleSession` 继续是状态与阶段的权威。

成功的标准不是 AI 看起来会说宝可梦术语，而是：它不偷看、不越权、不会因格式错误中断战斗、在同一输入下可审计、在网络失败时有可预测回退，并能用对局基准持续评估难度和质量。

## 当前可复用起点

当前架构已经有三项直接可用的能力：

- `BattleApplication` 为不同 `BattlePerspective` 构造观察，并提供该视角的 `legal_actions`。这是一条比直接序列化内部 `Battle` 更正确的 AI 输入边界。
- `BattleCoordinator<P: OpponentPolicy>` 已把对手行为抽象为 `choose_action(observation, legal_actions) -> Option<Action>`。当前 demo 策略可以被替换，但 coordinator 仍负责提交与阶段推进。
- `battle-ramus-adapter` 已把固定对战动作注册为能力受限的 Ramus 调用；`game-ramus-adapter` 已证明玩家和 AI 可通过相同 catalog 变成类型化游戏 intent。

这意味着第一版 AI 不需要设计一个会读写游戏状态的新协议。它需要的是把上述纯 Rust 接口投影成稳定 DTO，并在 adapter 侧处理模型调用、超时、解析、审计和回退。

## 威胁模型

AI 对战最危险的错误不是“输得不够聪明”，而是破坏公平或可恢复性。设计必须显式防范：

| 风险 | 错误方式 | 正确约束 |
| --- | --- | --- |
| 隐藏信息泄露 | 把整个 `Battle` 或完整双方队伍发给模型 | 只发送该对手视角的公开观察。 |
| 非法动作 | 模型返回任意招式名、字符串或工具调用 | adapter 只能接受动作 ID；应用层仍以 `legal_actions` 校验。 |
| 提示注入 | 对方昵称、招式名或 NPC 文本改变系统提示 | 数据全部作为明确字段编码，不能拼接为可执行指令。 |
| 超时/断网 | 等待模型导致战斗卡死 | 预算到期后用确定性回退动作继续。 |
| 不可重现 | 只记录最终动作，丢掉版本和上下文 | 记录观察哈希、可选集、策略版本、结果与原因。 |
| 成本失控 | 每回合附带大量历史和重试 | 固定令牌/时间/重试预算，超限降级。 |
| 规则污染 | 模型解释影响伤害或随机数 | 模型只选择动作；规则核心完全忽略解释文本。 |
| 假公平 | 离线训练策略接触完整状态后直接在线使用 | 训练/评估视角和公平对局视角使用不同类型。 |

威胁模型也适用于本地模型。离线不等于可信；本地 provider 仍可能返回损坏、过长、版本不匹配或不合法的值。

## 标准端口

未来应把现在的 `OpponentPolicy` 演进为能表达上下文、预算和诊断的端口，但保持其纯输入/输出性质。概念模型如下：

```text
OpponentDecisionPort
  decide(request) -> DecisionResult

DecisionRequest
  battle_id / turn / ruleset_version
  perspective observation
  legal action descriptors
  policy profile
  deadline and token budget
  correlation id

DecisionResult
  chosen action OR abstain
  public rationale summary (optional)
  provider metadata
  diagnostics / timing
```

真正的 Rust 类型名可在实现设计中再决定。以下约束应固定：

- `DecisionRequest` 不包含内部随机状态、对手未公开成员、未公开招式、未来事件、文件路径、令牌或玩家存档全文。
- `legal action descriptors` 必须是枚举出的稳定动作 ID，而不是让模型生成自然语言。在 UI 中显示的招式名称和在协议中使用的 ID 应分离。
- `DecisionResult` 只能包含一个动作引用或弃权。模型解释必须是可选展示/审计字段，永远不参与规则决策。
- deadline 是请求层的现实时间约束，不进入 `battle-domain`。核心只看到最终已选动作。
- correlation ID 用于日志和审计，不用作业务状态或随机输入。

如果模型 provider 支持工具调用，也不应把它暴露成任意工具目录。每回合只有一个逻辑工具：从服务器提供的 `legal_actions` 中选择一项。这个选择在 schema 中可被强制为枚举，在 adapter 外再被二次校验。

## 观察合同

AI 的输入应来自 `BattleObservation` 的一个专门投影，而不是直接向模型暴露 Rust debug 输出。投影需要稳定、有限、可版本化，并避免把表现层字段混入策略事实。

建议按五个区段组织：

| 区段 | 允许字段 | 不允许字段 |
| --- | --- | --- |
| 身份与版本 | 对局 ID、回合、规则包、AI 角色/难度 | 内部内存地址、构建机器信息。 |
| 自己方公开状态 | 活跃成员、已知队伍、HP 比例/数值、已知招式 PP、异常、能力阶级 | 对手私有数据。 |
| 对手公开状态 | 已登场成员、公开 HP、已展示招式、状态、公开天气/场地 | 未登场成员、未展示招式、内部概率。 |
| 阶段 | 正常回合、强制替换、对局已结束等 | UI 动画进度、玩家菜单焦点。 |
| 候选动作 | 动作 ID、动作类别、可展示摘要、可用性原因 | 不合法动作、未实现动作、自由文本命令。 |

是否提供精确 HP、百分比 HP、伤害范围或属性克制提示，是难度与产品设计问题。它必须作为 `AiInformationProfile` 的显式版本化选择。简单难度可以给更多公开辅助信息，高难度不等于给 AI 隐藏信息，而是使用更好的策略、搜索或更少随机失误。

观察投影必须有独立测试。测试至少断言：对手未公开队员不出现；对手未展示招式不出现；强制换人时只出现换人动作；已经结束的战斗不发起请求；同一 `BattleObservation` 按不同视角投影出的字段不同但各自合法。

## 动作合同

动作提交应沿用领域的 `Action` 语义，但对模型使用稳定协议标识。示例：

```json
{
  "request_id": "decision-...",
  "action_id": "move:slot-2"
}
```

`move:slot-2` 只在当前请求的合法动作表中有意义。不能让模型持久记住“slot 2 永远是某个招式”；换人、PP、禁用和强制替换会改变可选集。适配器完成以下步骤：

1. 检查响应体大小、编码、schema 版本与请求关联 ID。
2. 取出 `action_id`，只在本请求的合法动作表中查找。
3. 找不到、重复、含额外未允许字段或请求过期时，返回结构化失败而非猜测。
4. 应用层再次调用当前阶段的 `legal_actions`，防止决策期间状态已推进。
5. 只有二次校验通过后才提交 `Action` 给 `BattleApplication`。

这里的双重校验不是冗余。第一次是边界输入校验，第二次是状态机校验。若异步请求期间玩家或系统状态变化，旧响应不应被错误提交到新回合。

## 策略分层

不要只实现“模型 AI”。至少应有三个可替换策略层，且都使用同一个端口：

| 层 | 用途 | 特征 |
| --- | --- | --- |
| 规则型保底策略 | 离线、测试、超时回退 | 纯、快速、确定性；例如优先可用招式或合法换人。 |
| 启发式策略 | 正式基础难度 | 依据公开状态、伤害估计、HP、异常和角色配置评分。 |
| 模型/搜索策略 | 高难度、实验和研究 | 受预算限制；只能输出候选动作。 |

规则型策略必须先完成，因为它既是产品回退，也是契约测试 oracle。它不需要很强，但必须永远返回当前合法集中的一个动作，或在没有动作时给出明确 `NoActionAvailable`。模型策略的质量应该和它比较，而不是只看主观“像人在打”。

启发式策略可作为过渡，也可长期保留。它可用相同规则包计算公开的伤害区间、速度关系和风险值；但不能为了方便读取隐藏值。为防止策略过拟合某个 UI 或模型描述，策略输入只能是标准观察 DTO。

## 模型 adapter

模型 adapter 的职责是外壳工作：选择 provider、构造请求、执行网络或本地推理、限制长度/时间、解析结构化响应、清洗元数据、生成审计记录。它不做以下事情：

- 不计算伤害或决定合法性；
- 不读取或修改 `Battle`、`GameState`、存档文件；
- 不在 provider 错误时自行编造一个看似合理的领域动作；
- 不把模型返回的理由写入世界文本、训练师设定或长期状态；
- 不把 API key、完整提示、玩家个人数据写进普通游戏日志。

远程 adapter 还需有连接池、代理、速率限制、重试和费用观测，但这些不应污染上层决策模型。建议在一个适配器请求内最多一次主调用和一次有限重试；超出预算立即回退。每场战斗还应有总预算，避免异常回合循环累积成本。

## 回退策略

回退不是异常路径，它是产品功能。下面表格定义建议行为：

| 情形 | adapter 结果 | 对局行为 | 审计事件 |
| --- | --- | --- | --- |
| 正常合法响应 | `Chosen(action)` | 提交模型选择 | `AiActionAccepted`。 |
| 格式不合法 | `InvalidResponse` | 使用保底策略 | `AiFallback{invalid_response}`。 |
| 响应动作不合法 | `RejectedAction` | 使用保底策略 | `AiFallback{illegal_action}`。 |
| 超时 | `TimedOut` | 使用保底策略 | `AiFallback{timeout}`。 |
| 网络/服务失败 | `ProviderUnavailable` | 使用保底策略 | `AiFallback{provider_unavailable}`。 |
| 预算耗尽 | `BudgetExceeded` | 本局后续回合固定回退 | `AiDisabledForBattle`。 |
| 规则包/协议不匹配 | `VersionMismatch` | 禁用该模型配置，启动前或回合前给出诊断 | `AiConfigurationRejected`。 |

对玩家的呈现应该克制。无需显示“HTTP 502”。可以在开发模式显示细节，在正式游戏中保持对手行动节奏一致。最重要的是实际战斗事件仍由规则核心产生，回放无需依赖模型再次在线调用。

## 审计与隐私

AI 对战审计至少需要两个层级。

产品级记录用于复现：规则包版本、内容/训练师版本、初始战斗状态哈希、每回合观察哈希、合法动作哈希、选择动作、回退原因、策略版本、耗时和最终事件哈希。它不需要保存完整模型文本。

开发级记录用于诊断：经过脱敏的结构化请求、响应 schema 结果、provider 名称、模型版本、计费/令牌统计、错误类别和关联 ID。它必须有保留期、访问控制和开关。不要把玩家名称、聊天内容、完整存档或密钥混进训练/调试数据。

为了支持“为什么这局结果不同”，回放记录以规则输入和动作序列为准。模型审计只能解释动作选择过程，不能替代规则回放。

## 提示与角色设计

若使用语言模型，提示词的职责是约束输出格式和策略风格，而不是把规则全文塞进去。模型得到的仍然是标准 DTO。训练师角色可通过可版本化配置表达：风险偏好、换人阈值、是否偏好状态招式、是否保守使用有限 PP、故事语气。角色配置不能拥有“忽略合法动作”“读取对手隐藏队伍”或“修改暴击率”这类权力。

一个好的策略提示只需要：身份、目标、公平约束、当前观察、合法动作枚举、输出 schema、禁止输出额外文本。任何对战规则解释都应以简短、字段化摘要提供；复杂细节由规则型策略或模型训练数据承担。提示越长，越难版本化、越容易携带过期规则，也越昂贵。

## 评估基准

模型 AI 不应只靠试玩评价。建立一个固定的对局基准库：每个案例都冻结规则包、双方队伍、初始状态、随机种子、观察可见性、对手角色和最大回合数。基准分四类：

| 类别 | 问题 | 例子 |
| --- | --- | --- |
| 合法性 | 能否总在合法集中选动作 | PP 为零、强制换人、对局结束。 |
| 战术 | 能否在公开信息下避免明显错误 | 残血换人、属性克制、可击杀判断。 |
| 鲁棒性 | 失败时是否正确回退 | 缺字段、超时、旧版本响应。 |
| 产品难度 | 是否符合训练师定位 | 新手路线、馆主、终局对手。 |

报告至少包含合法动作率、回退率、超时率、平均回合延迟、对保底/启发式的胜率、按规则包的回归差异，以及人工审阅的少量代表性回放。胜率不能单独代表质量：一个通过隐藏信息获胜的策略得分应为零。

## 实现阶段

### A1：纯策略合同

定义 AI 观察投影、动作描述、决策结果和结构化失败。实现保底策略与至少一个启发式策略。用现有 `battle-session` 跑通，无网络、无模型。退出条件是所有策略在任意阶段只返回合法动作，且回放与不使用 AI 的对局一致。

### A2：异步边界与回退

在 runtime/application 外壳中加入 deadline、取消、关联 ID、预算和回退。不要把 async runtime 传到领域。退出条件是断网、慢响应、错误 JSON、过期响应和重复响应都能被测试模拟，且战斗不会卡住或状态错位。

### A3：第一个模型 provider

选择一个可配置 provider，接入严格 schema 响应。模型只控制一个训练师难度档，默认关闭或实验性开启。退出条件是基准合法性达到 100%，超时/失败均可回退，审计信息足以复现每个选择。

### A4：内容化对手人格

把策略 profile 放入训练师内容包，允许编辑器选择规则型、启发式或模型策略以及预算。退出条件是内容作者无法通过配置扩大权限，发布校验能拒绝不兼容模型/规则组合。

### A5：持续评估

把基准、回放差异和成本指标纳入 `ops` 质量入口。模型升级、提示改动、规则包升级和 DTO schema 改动都需要运行对应基准。退出条件是没有“悄悄变聪明或变笨”的不可解释上线。

## 不在本提案中决定的事项

- 模型供应商、模型名称、部署区域、价格和账号流程。
- 是否训练自有策略、使用强化学习、搜索深度或外部对战数据库。
- 玩家是否可以观看 AI 的简短说明或完整回放分析。
- AI 难度的商业呈现、可访问性选项和最终数值平衡。
- 联机对战中是否允许 AI 代打；在单人规则稳定前不讨论此项。

## 完成标准

AI 对战 MVP 的完成定义是：

1. 对手策略只从按视角过滤的观察与合法动作表获得信息。
2. 保底、启发式和模型 adapter 使用同一动作合同，且都经过二次状态校验。
3. 模型失败、超时、旧响应、非法响应和预算耗尽不会中断对局或损坏回放。
4. 每个模型动作都有可脱敏审计记录；战斗回放不需要重新调用模型。
5. 固定基准证明合法性、鲁棒性和难度分布，且基准随规则包版本冻结。
6. 运行期 AI 仍可完全关闭，游戏使用本地策略继续可玩。

满足这些条件后，AI 才是一个可维护的对战能力，而不是一个脆弱的演示效果。
