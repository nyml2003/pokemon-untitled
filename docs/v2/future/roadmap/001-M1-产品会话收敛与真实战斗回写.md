# M1：产品会话收敛与真实战斗回写

> 分类：未来；最后整理：2026-07-21。
> 状态：第一个里程碑的实施分解。本文不代表所列类型、crate 或 API 已经存在。

## 里程碑目标

将当前两条已验证但分离的路径收敛为一条产品会话：世界移动和 NPC/遭遇触发来自实际世界状态；战斗由真实 `BattleSession` 执行；战斗结束由一个受验证的结果补丁原子回写到长期 `GameState`；重载后得到一致的队伍、世界和训练师状态。

M1 不实现现代规则包、动态 NPC DSL、AI 地图或模型 AI。它只建立这些能力共同依赖的最小闭环。为避免范围漂移，M1 允许继续使用一个小型预制区域、有限队伍和既有第三世代风格规则；但不允许再使用 `ResolveBattle { outcome, hp, pp }` 作为正式运行路径的替代品。

## 当前事实与缺口

| 当前能力 | 已有所有者 | M1 发现的缺口 |
| --- | --- | --- |
| 世界移动、草丛遭遇、场景切换与实际回放 | `game-session` + `world-application` + `battle-session` | 使用 demo roster/seed；没有持久队伍、经济、训练师完成状态或存档。 |
| 玩家状态、NPC capability、warp、商店、训练师一次性状态、JSON 存档 | `game-foundation` | 用 `ResolveBattle` 摘要输入，不持有真实战斗会话和回放。 |
| 确定性战斗、视角观察、合法动作、事件历史 | `battle-domain` + `battle-application` + `battle-session` | 没有产品级结果映射到 `GameState`。 |
| 原生装配和输入/场景表现 | `game-host` | 产品基础页已装配 `ProductSession`；仍待 Windows 原生窗口验收。 |

M1 的设计问题不是“再写一个统一 struct”。它必须先定义唯一所有者：长期玩家状态归产品会话内部的 `GameState`；对战执行期间的短期规则状态归 `BattleSession`；世界位置/阻挡归世界 reducer；presentation 只消费快照。任何相同业务字段不能同时由 demo session 和 foundation state 分别写入。

## 最小玩家切片

M1 只验收以下流程。流程每一步都需要 application 层测试；最后再在 host 验证实际输入和表现。

```text
新游戏
  -> 在小型预制地图移动
  -> 与赠送 NPC 交互，获得起始队伍
  -> 进入草丛，得到确定的遭遇输入
  -> 创建真实 BattleSession
  -> 提交玩家动作，对手使用现有确定性策略
  -> 完整播放并结束战斗
  -> 从真实最终状态构造 BattleResultPatch
  -> 原子回写 HP、PP、异常、经验、奖励和世界结果
  -> 与训练师战斗，胜利后只记录一次完成状态
  -> 保存，重启，加载后继续同一状态
```

第一版可将逃跑、失败、异常和多只队伍成员作为明确的最小子集处理，但不能假装不存在。每个未支持路径应在开战前或动作提交时得到类型化拒绝；不允许进入半完成战斗再丢弃状态。

## 目标边界

### 产品会话

引入一个产品层的会话聚合或编排服务。名称可在实现前决定，但职责必须固定：持有当前 `GameState`、已加载的静态内容、当前世界投影、可选活动战斗及其生命周期；接收类型化玩家/系统命令；返回新的会话、类型化事件和只读快照。

它不直接实现伤害、碰撞、库存或窗口。它调用/组合 `world-domain`、`world-application`、`battle-session`、`game-foundation` 的值对象与规则。若发现现有 crate 的依赖方向阻止这个组合，先写小型接口/数据映射，不把 adapter 或 runtime 依赖拖进 domain。

### BattleStartRequest

真实开战不应从 `roster_seed` 或 demo 函数隐式生成。定义一个显式开战请求，至少包含战斗来源（野生/训练师）、规则/内容版本引用、玩家队伍快照、对手队伍定义、初始随机输入、奖励策略和事件返回入口。它由世界/事件触发器创建，由产品会话验证后构造 `BattleApplication`、`BattleCoordinator` 和 `BattleSession`。

M1 可以使用简单预制训练师/野生队伍，但它们必须经稳定 ID 查询，不再由 host 直接拼装。以后 M2 的规则包和 M3 的内容包只需替换请求来源，不应改写 battle 生命周期。

### BattleResultPatch

真实战斗结束后，产品会话从 `BattleSession` 的最终观察和规则/内容奖励定义构造结果补丁。补丁需区分：队伍变更、战斗结果、奖励、训练师状态和事件恢复信息。它不是 presentation 的 HP 文本，也不是模型输出。

补丁构造与应用必须两阶段：先从终局 battle 状态和活动战斗上下文构造候选；再在克隆 `GameState` 上验证并一次性应用。失败时保留活动战斗和原 `GameState`，返回可诊断错误。禁止在补丁应用前先清空 `active_battle`。

### 存档检查点

M1 至少支持世界安全点的保存/加载。是否保存进行中战斗可以先做明确限制：若尚未实现可恢复战斗快照，保存命令在活动战斗中返回 `SaveUnavailableDuringBattle` 或等价错误；不要把只保存一半队伍状态的文件写入磁盘。完成世界安全点后，再将进行中战斗可恢复性作为后续工作项。

工作包按顺序执行。每包结束后保留代码、测试和短设计记录；未完成的包不得用 runtime 手工验证代替。

### W2：定义跨会话数据合同（已完成：2026-07-21）

**目标**：先定义类型化边界，再连实现。

### W3：实现真实战斗启动桥（已完成：2026-07-21）

**目标**：用 `GameState` 的持久队伍和内容定义创建真实 `BattleSession`。

**动作**：

1. 将现有 `CreatureState`/训练师定义映射为 battle 所需的 `Team`、`Pokemon`、`Move`、能力值和初始状态；未支持字段明确拒绝。
2. 让野生遭遇和训练师交互只产生 `BattleStartRequest`，由产品会话统一创建活动战斗。
3. 复用 `BattleCoordinator`/`OpponentPolicy`，先使用确定性本地策略；不接模型。
4. 替换或隔离 `game-session` 的 demo roster 创建，使其不再成为产品路径的唯一队伍来源。

**产物**：从世界事件进入真实 `BattleSession` 的 application 测试。

**验收**：同一持久队伍进入战斗时，战斗初始 HP/PP 与 `GameState` 一致；非法启动不改变世界或存档状态。

**执行记录**：[W3/W4 真实战斗与原子回写](m1/003-W3-W4-真实战斗与原子回写.md)。

### W4：实现结果补丁与原子回写（已完成：2026-07-21）

**目标**：消除正式路径对 `ResolveBattle { outcome, hp, pp }` 的依赖。

**动作**：

1. 从 `BattleSession` 终局状态构造 `BattleResultPatch`，包含所有 M1 支持的 HP、PP、异常、经验、金钱、训练师完成和遭遇清理结果。
2. 在 `GameState` 或明确的 application service 中应用补丁，复用库存、金钱、队伍和 flag 不变量。
3. 定义胜利、失败、逃跑（若首发允许）、非法结束、重复奖励和补丁冲突的行为。
4. 保持事件顺序：战斗结束事实先形成，长期状态成功更新后才发出“返回世界/继续事件”。

**产物**：结果映射器、原子应用入口、正例与失败测试。

**验收**：战斗胜利后可见 HP/PP/经验/金钱/训练师状态与终局一致；补丁被拒绝时原 `GameState` 和活动战斗都未被破坏。

**执行记录**：[W3/W4 真实战斗与原子回写](m1/003-W3-W4-真实战斗与原子回写.md)。

### W5：收敛世界、事件与场景快照（已完成：2026-07-21）

**目标**：让 runtime 只消费统一产品会话的快照和事件。

**动作**：

1. 定义产品快照中世界、活动战斗、可用输入和存档可用性的投影。
2. 让输入归一化仍在 runtime/presentation，向产品会话提交移动、交互、战斗动作、回放推进和离开完成战斗等类型化命令。
3. 保留 `BattleSession` 的回放锁定语义；presentation 不可在播放期间提交新动作。
4. 将当前 `GameSession` 的 demo 特有 API 标记为迁移对象，先通过 wrapper 或 adapter 保持编译，再逐步删除没有消费者的路径。

**产物**：统一 snapshot/event 投影、迁移清单、无窗口应用测试。

**验收**：运行时不需直接读取 `GameState` 内部或 `Battle` 内部；从世界进入战斗再返回的场景切换没有第二份状态。

## 推荐实现顺序

严格顺序是 W1 -> W2 -> W3 -> W4 -> W5 -> W6 -> W7。W1 与 W2 可能是短设计/测试工作，W3 与 W4 是里程碑核心，W5/W6 是将核心接回产品的必要闭合，W7 是退出门而不是可选清理。

不要在 W3 前重构 UI、接模型或批量扩展对战规则。不要在 W4 前删除现有摘要 API；它可以暂时保留给旧薄切片测试，但必须没有正式产品路径依赖。不要在 W6 前声称已经具备可保存游戏。

## 测试矩阵

| 层级 | 关键问题 | M1 必需案例 |
| --- | --- | --- |
| 值与领域 | 映射输入合法吗？ | 不支持队伍字段、非法 HP/PP、未知 ID、重复成员。 |
| BattleSession | 战斗能否完整结束？ | 动作、回放、强制替换、结束阶段和最终观察。 |
| 结果映射 | 终局如何变成持久补丁？ | 胜利、失败、训练师奖励、野生遭遇清理、补丁拒绝。 |
| 产品会话 | 状态是否只有一个 owner？ | 移动 -> 遭遇 -> 战斗 -> 回写 -> 世界。 |
| 存档 | 重载是否一致且拒绝损坏？ | 成功保存、内容不匹配、checksum 错、活动战斗策略。 |
| Runtime | 输入和场景是否正确装配？ | 实际进入战斗、播放、退出、保存入口。 |

每个失败测试都断言原状态。只断言返回错误不够；需要比较 `GameState`、活动战斗上下文和关键事件没有被部分修改。

## 风险与处理

| 风险 | 早期信号 | 处理 |
| --- | --- | --- |
| 过早新建第三套状态 | 新类型复制位置、队伍、金钱和战斗字段 | W1 强制所有权矩阵；新类型仅编排或引用。 |
| 结果映射丢失信息 | 只能得到 HP/PP，无法解释异常/奖励 | W2 先定义补丁，W4 用终局观察和内容规则构造。 |
| demo 路径泄漏 | 正式测试仍调用 `demo_teams` 或 `roster_seed` | W3 在测试中断言显式 `BattleStartRequest` 来源。 |
| 回放与状态不同步 | 动画完成后最终观察不一致 | 复用 `BattleSession` settled observation；W5 不重算表现。 |
| 存档在不安全状态写入 | 重载后活动战斗或 flag 半更新 | W6 明确安全点/拒绝策略并做故障测试。 |
| 范围膨胀 | 开始加入规则包、AI 或地图生成 | 以本页非目标和 W7 退出条件拒绝扩展。 |

## M1 退出条件

M1 完成必须同时满足：

1. 一个产品会话拥有唯一的长期 `GameState`，并协调世界与活动 `BattleSession`。
2. 世界遭遇和训练师交互以明确请求创建真实战斗，不依赖 demo roster/摘要结果作为正式路径。
3. 真实战斗终局产生 `BattleResultPatch` 或等价受验证合同，原子更新队伍、奖励和世界状态。
4. `ResolveBattle { outcome, hp, pp }` 不再被正式产品会话调用；若保留，仅限兼容/旧测试并有删除计划。
5. 新游戏、赠送、野生战、训练师一次性奖励、保存和加载在同一 application 场景中可重复通过。
6. 失败路径不部分修改长期状态、活动战斗或存档文件。
7. 所有必要验证通过 `ops` 执行；若原生 host 未验收，里程碑不得标为完成。

达到这些条件后，M2 与 M3 才可开始把规则和内容系统扩展为正式产品能力。
