# 产品开发路线图

> 分类：未来；最后整理：2026-07-22。
> 状态：执行计划。里程碑按依赖顺序排列，不承诺日期；完成条件优先于完成时间。

## 路线结论

先让产品拥有一条真实、可保存、可回放的游戏会话，再把规则、内容与模型能力逐层接入。任何里程碑都不得要求模型、UI 或 runtime 绕过纯状态转换直接修改游戏事实。

M1 的代码与 Linux 验证已完成，仍等待 Windows 原生验收；其后续 M2 的本地实现已完成并保留该发布门槛。M3 已完成内容包身份、存档引用及产品 host 的静态 JSON 导入，下一项是事件 DSL。当前实施记录见 [M2：规则包与前 386 MVP](002-M2-规则包与前386MVP.md) 与 [M3：静态内容包与事件 DSL](003-M3-静态内容包与事件DSL.md)。

## 里程碑总览

| 里程碑 | 目标 | 主要前置 | 退出条件 |
| --- | --- | --- | --- |
| M1 产品会话收敛 | 用真实 `BattleSession` 完成世界遭遇、训练师战和持久状态回写。 | 现有 `game-session`、`game-foundation`、`battle-session`。 | 单一产品会话可从移动进入实际战斗，将合法结果原子回写并保存/重载。 |
| M2 规则包与前 386 MVP | 冻结首发规则包、前 386 内容允许表与回放语料。 | M1 的真实战斗桥接。 | 已在本地实现并验证；首区域所有队伍/招式/能力均可由规则包验证，固定输入可重放。发布仍等 M1 原生门槛。 |
| M3 静态内容包与事件 DSL | 将起始区域的地图、NPC、训练师、文本和事件从 demo/常量路径纳入版本化内容包。 | M1；M2 的规则引用。 | W1/W2 已将 `starter-region@1` 及其 JSON 内容接入 host 与存档；完成时新游戏到训练师战后续体由静态 Rust DSL 与内容包驱动。 |
| M4 动态 NPC DSL | 让本地模型在闲时生成动态 NPC DSL 候选，由 Rust 编译、模拟并在安全点激活。 | M3 的事件运行时、内容包与存档引用。 | 模型不可用时仍执行旧 DSL；激活修订可保存、回放、回退。 |
| M5 AI 对战 | 提供视角过滤观察、动作 schema、保底策略、模型 adapter 和对局基准。 | M2 的规则/回放；M3 的训练师内容。 | 人类、启发式和模型对手只从合法动作集中选择，失败可回退。 |
| M6 AI 地图创作 | 以候选 schema、约束求解、校验和编辑器审阅生成地图/区域。 | M3 的内容包和地图引用；M2 的遭遇/训练师合法性。 | 候选地图可达、可加载、可审阅；未经批准不进入发布内容。 |
| M7 首个可发行区域 | 完成完整区域、存档迁移、质量门槛、平台试玩和发行资料。 | M1 至 M6。 | 离线可完成整条垂直切片；内容、动态 DSL、规则和存档可追溯与回退。 |

## 依赖图

```text
M1 产品会话收敛
  -> M2 规则包与前 386 MVP
  -> M3 静态内容包与事件 DSL
       -> M4 动态 NPC DSL
       -> M6 AI 地图创作
  -> M5 AI 对战
M2 + M3 + M4 + M5 + M6
  -> M7 首个可发行区域
```

M2 与 M3 可以在 M1 完成后部分并行，但不能以临时摘要战斗或第二份玩家状态替代 M1。M4、M5、M6 的技术预研可以独立进行，但任何进入正式游戏的实现都必须等待它们的前置里程碑。

## 阶段门槛

每个里程碑开始前、实现中和结束后都使用相同的判断方式。

| 时间点 | 必须回答的问题 | 允许的证据 |
| --- | --- | --- |
| 开始前 | 当前所有者、输入、输出、失败和非目标是什么？ | 现有源码、manifest、测试、已批准产品文档。 |
| 实现中 | 新状态是否有唯一所有者；副作用是否仍在外层；失败是否保持原状态？ | 类型、单元/场景测试、结构化诊断。 |
| 结束时 | 同一条玩家切片是否真实经过新能力；能否保存、重放或回退？ | application 测试、内容检查、`ops` 验证、必要的原生验收。 |

“代码已编译”不是里程碑完成。“模型能返回一段文本”也不是模型里程碑完成。退出条件必须证明它已进入产品循环而没有扩大权限或引入第二份事实源。

## 横切工作

以下工作贯穿全部里程碑，但不单独取代功能目标：

- **架构与所有权**：保持 `runtime -> adapter -> presentation -> application -> domain -> foundation` 的依赖方向。新增状态需明确聚合根与保存边界。
- **规则与数据**：每个内容引用都通过规则包和数据版本校验；禁止由 UI 或模型猜测合法性。
- **存档与回放**：新长期状态必须有版本、验证、迁移/拒绝策略；关键战斗和事件可由输入重演。
- **模型边界**：静态与动态 NPC 共用一套 DSL、编译器、中间表示、执行器和测试工具。静态内容与 DSL 执行归 Rust；动态 NPC 由本地模型在 `CapabilityProfile` 限制下提出同一 DSL 的候选修订，Rust 编译、模拟、在安全点激活。
- **质量**：纯测试优先，运行时/窗口验证补充真实装配与表现问题；所有公共验证经 `ops` 执行。
- **文档**：实现事实进入 current/crate 文档；路线图只保留未完成任务、当前阻塞与退出条件。

## 当前后续

M2 已冻结当前 `legacy-gen3@1` 基线；M3 的下一项工作是 W3，用静态事件 DSL 取代当前 NPC capability 的预制交互分支。M4、M5、M6 只保留接口预研，直到它们能引用稳定的规则、内容和产品会话合同。M1 的 Windows 原生验收仍是发布排序门槛，不应因 M2 或 M3 的本地证据而跳过。
