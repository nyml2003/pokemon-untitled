# W3/W4：真实战斗启动与原子回写

> 归属：M1 产品会话收敛与真实战斗回写。
> 状态：已完成；记录日期：2026-07-21。
> 实现位置：`game-session::ProductSession`、`game-session::roster`、`game-foundation::GameState`。

## 结果

`ProductSession` 已成为 M1 的 application 编排入口。它持有 `CurrentDataSet`、`ThinSliceContent`、唯一的长期 `GameState` 和可选 `ProductBattleSession`。移动、交互、warp、遭遇和购买先进入 `GameState`；训练师交互和草丛遭遇取得活动战斗事实后，才通过已验证的 `BattleStartRequest` 创建真实 `BattleSession`。

本轮没有把 demo roster 改造成产品数据。产品队伍由 `GameState::party` 的 `CreatureState` 映射，对手由静态 `BattleDefinition` 和 `TrainerDefinition` 映射。M2 规则包校验后，`route-wild` 以静态 `WildOpponentDefinition { species: "Torchic", level: 3 }` 描述对手，训练师队伍为 `Bulbasaur`；两者与玩家 `Treecko` 都是当前 `legacy-gen3@1` 可执行组合。M1 明确只支持一只持久队伍成员、一个真实出战者和一只训练师/野生对手；映射器会用零 HP 的战斗保留位满足引擎队伍形状，不向玩家暴露虚构换人选项。多成员、异常状态与完整招式集保留为后续内容/规则工作，不被伪装成已持久化能力。

## 回写边界

战斗完成时，`ProductSession` 只从 `BattleSession` 的 settled observation 读取己方参战者 HP 和首个招式 PP，并用活动 `BattleStartRequest` 构造 `BattleResultPatch`。补丁经 `BattleResolution` 进入 `GameState::apply_battle_resolution`：

1. 在克隆候选状态上核对活动战斗 ID、参战宝可梦 ID、HP 和 PP。
2. 依据静态 `BattleDefinition` 计算胜利奖励及训练师完成状态。
3. 成功时一起更新队伍、经验、金钱、训练师标记并清除活动战斗。
4. 任一步失败则保留原 `GameState` 和 `ProductBattleSession`，不产生半结算。

旧 `GameCommand::ResolveBattle { outcome, hp, pp }` 仍为 foundation 兼容路径存在，但 `ProductCommand` 没有对应变体，runtime 也明确拒绝将它路由为产品命令。

## 验证

`game-session/tests/unit/product_session.rs` 覆盖：

- 从持久队伍进入真实野生战时，战斗初始 HP/PP 等于 `GameState`；
- 野生和训练师战结束后，经验、金钱、HP/PP、活动战斗和一次性训练师状态一致；
- 战斗中世界命令被拒绝且快照不变；
- 错误的 `BattleResolution` 不会破坏原活动战斗或玩家状态；
- 同一场景可完成新游戏、赠送、两场真实战斗、购买和重载。

W3/W4 由 `ops format` 与 `ops test --suite core` 验证。W5/W6 负责将该会话接到 runtime、完成实际文件保存策略和扩大 workspace 验收。
