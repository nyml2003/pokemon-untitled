# M3：静态内容包与事件 DSL

> 分类：未来；最后整理：2026-07-22。
> 状态：W1 与 W2 的产品 host 路径已完成本地实现与验证；事件 DSL、编辑器/CLI 共用导入路径尚未开始。

## 目标

M3 让起始区域的静态内容成为可识别、可校验、可随存档恢复的产品输入，并在其上建立静态 NPC 的 Rust DSL 执行路径。这里的“静态”指发行时冻结、由 Rust 负责解释和校验的内容；它不依赖模型在线返回，也不在交互过程中任意改写 `GameState`。

终态不是把一批 JSON 放进资源目录，而是建立以下可验证关系：

```text
内容包 manifest
  -> 静态地图 / NPC / 训练师 / 文本 / 事件程序
  -> ProductSession
  -> SaveEnvelope 中的内容包与规则包引用
  -> 仅在匹配版本下恢复
```

这也是 M4 动态 NPC 的前置。动态能力只能生成同一 DSL 的候选修订；候选由 Rust 编译、模拟并在安全点激活。它不会拥有独立 flag、随机启发式状态或第二份剧情事实。

## 非目标

- 不在 M3 引入大模型调用、闲时调度或动态修订仓；这些属于 M4。
- 不把任意脚本文本直接解释为游戏效果；所有事件都必须先经过 Rust 定义的语法、类型和权限校验。
- 不改变 `legacy-gen3@1` 的对战范围，也不让内容包绕过 `BattleRuleset` 的队伍准入。
- 不要求第一版内容包实现网络下载、签名服务或通用 mod 平台。

## 已完成：W1 内容包身份与存档契约

当前实现增加了 `game-foundation::ContentPackageManifest` 与 `ContentPackage`。manifest 使用稳定的 `ContentPackageId`，并固定以下最小合同：

| 字段 | 当前 `starter-region@1` 值 | 用途 |
| --- | --- | --- |
| package + revision | `starter-region@1` | 唯一识别可恢复的静态内容集合。 |
| content version | `thin-slice-v3` | 必须与实际 `ThinSliceContent` 一致。 |
| data reference | `embedded-pokeapi-gen3-v1` | 记录内容依赖的数据快照。 |
| ruleset reference | `legacy-gen3@1` | 约束训练师、野生队伍和战斗合同。 |

`ContentPackage::new` 会拒绝零 revision、空引用和 manifest/内容版本不一致。当前 `ThinSliceContent::standard()` 仍是静态 Rust 构造器；W1 把它封装进 `ContentPackage::standard()`，没有把尚未定义的 JSON schema 伪装成已完成的外部格式。

`ProductSession` 现保存该 manifest，并在建立会话时校验内容包要求的规则引用等于内建 `legacy-gen3@1`。新建产品存档会同时写入规则包和内容包存储键；`ProductSession::from_package_save` 缺少任一引用或与当前包不一致时拒绝恢复。旧的 `ProductSession::{new,from_state,from_save}` 继续以 `starter-region` manifest 包装传入的 `ThinSliceContent`，以免 runtime 装配在本工作包中被迫迁移。

本工作包的回归测试覆盖：

- manifest 拒绝零 revision 和内容版本不一致；
- 产品存档写入 `legacy-gen3@1` 与 `starter-region@1`；
- 使用其他内容包引用的存档无法恢复；
- 既有的真实野生战、训练师战、保存和重载路径仍通过全量测试。

## 已完成：W2 产品内容包导入

`assets/content/starter-region/content.json` 现在是产品 host 的静态输入。`ContentPackageDocument::from_json` 解析受限 schema，随后以 `ContentDefinitions` 构造 `ThinSliceContent`；构造过程验证地图尺寸/出生点、warp 目标、NPC 位置、商店物品、战斗、训练师和遭遇引用。JSON 只携带声明式内容，文件读取仍在 `game-host` runtime 边界。

`game-host` 读取该文件后调用 `ProductSession::from_package`。这移除了 host 装配时以 `trainers-v1.json` 覆盖产品内容的旧路径，也保证规则包会在启动时校验 JSON 中的训练师/野生队伍。当前 `route-rival` 使用已被 `legacy-gen3@1` 支持的 `Bulbasaur`；不支持能力的 `Zigzagoon` 不再进入产品会话。

已覆盖的测试包括 JSON 内容与旧薄切片内容等价、manifest/内容版本绑定、存档包引用匹配，以及 host 装配中的 `JSON -> ProductSession`。缺失或错误引用会在读取后、创建会话前返回结构化错误，不能降级为空内容。

仍待完成：让命令行薄切片和编辑器经同一文件 loader 工作，并将内容 schema 的格式版本、错误诊断和场景检查提升为独立 `ops` suite。这些属于 W4 的交付检查，不阻塞 W3 建立静态事件 DSL。

## W3：静态事件 DSL 与预制文本

复用 `narrative-token`、`narrative-compiler`、`narrative-cps` 已有的基础表达能力，先定义游戏事件运行时需要的最小指令集和权限，而不是另建“AI 专用脚本语言”。第一版只需覆盖起始切片：面向、移动、显示预制文本、条件判断、写授权 flag、给予已定义物品、启动已定义战斗、结束或安全暂停。

事件程序的读写集合必须在编译时可见。比如教授的脚本可以读取“是否已有初始队伍”并写入对应领取 flag，但不能直接改钱、跨 NPC 写私有状态或构造任意战斗队伍。`GameState` 仍是唯一长期事实所有者，DSL 只产生类型化命令/效果，由产品会话原子提交。

**退出条件**：起始区域内教授、商店、训练师和路线引导均由内容包中的静态 DSL 与预制文本驱动；脚本失败不部分提交状态；对话/事件 continuation 可在安全点保存并恢复。

## W4：内容场景、迁移与发布检查

为每个内容包提供无窗口 scenario：加载、开局、领取、移动、野生战、训练师战、商店、保存、重载。再增加内容包 revision 变化时的迁移/拒绝策略，并把内容检查纳入 `ops`。

**退出条件**：相同内容包、规则包与输入可重放；不兼容包或缺失 revision 不静默加载；内容场景、规则合法性、DSL 编译和存档恢复都能以公共 `ops` 入口验证。

## 验收顺序

1. W1 已证明“保存的是哪个内容包”；W2 已证明产品 host 的静态内容来自该包文件。
2. W3 在稳定内容合同之上接入同一套静态/动态 DSL，先完成预制文本和受限事件。
3. W4 将编辑器/CLI 内容装配、内容场景、迁移和发布检查产品化，随后 M4 才可让本地模型生成 DSL 候选。

任何阶段都不能把模型输出当作直接命令，也不能为方便加载而跳过 `ContentPackage`、`BattleRuleset` 或 `GameState` 的验证。
